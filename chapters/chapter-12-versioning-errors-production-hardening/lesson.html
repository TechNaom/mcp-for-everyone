Versioning, Errors & Production Hardening

Chapter 3 described the modern/legacy compatibility story from the spec. This chapter actually connects a legacy-mode client to a modern server and shows you exactly what happens — plus the error patterns you need to harden a server against before it ships.

Chapter 3 laid out the compatibility matrix from the spec: modern client + legacy server fails, legacy client + dual-era server works, and so on — all sourced from the specification text. This chapter closes the loop by actually connecting a legacy-mode client to the real servers this course has been building, and reading what genuinely happens on the wire.

Proof: The SDK Is Dual-Era By Default

The Python SDK's Client accepts a mode parameter — "auto" (default) or "legacy", forcing a real initialize/initialized handshake instead of the modern stateless flow. Connecting both modes to the exact same MCPServer instance:

dual_era_test.py 
async with Client(mcp, mode="auto") as client:
    print("auto mode:", client.protocol_version)

async with Client(mcp, mode="legacy") as client:
    print("legacy mode:", client.protocol_version)
output 
auto mode protocol_version: 2026-07-28
legacy mode protocol_version: 2025-11-25

Both succeed. Debug logging on the legacy-mode connection shows a real notifications/initialized exchange — the actual legacy handshake, not a simulation. The same server, with zero extra code from you, correctly serves a caller that only knows the old spec and a caller that speaks the new one.

What "Dual-Era by Default" Means for You

Chapter 3's compatibility matrix has a row for exactly this: "Legacy client, Dual-era server → Works." Every server built in this course, without anyone writing version-handling code, is already a dual-era server, because that's the SDK's default behavior. This is genuinely good news — but it comes with a responsibility: you can't assume every caller speaks the version you tested against, because the server itself doesn't enforce one. A caller you've never tested with (an older client library, a partner's legacy tooling) can connect successfully and get served — which is great for compatibility, and also means your testing needs to cover both eras if you care about behavior parity between them, not just "does it connect."

Build: Hardening Against Bad Input

Version handling is one axis of production readiness; input validation is another. Every tool's type hints already generate real validation — tested against missing and wrong-typed arguments:

terminal — missing argument 
await client.call_tool("add", {"a": 1})  # missing 'b'
# is_error: True
# "1 validation error for addArguments
#  b
#    Field required [type=missing, input_value={'a': 1}, input_type=dict]"
terminal — wrong type 
await client.call_tool("add", {"a": "not a number", "b": 2})
# is_error: True
# "1 validation error for addArguments
#  a
#    Input should be a valid integer, unable to parse string as an integer"

This is free — the SDK generates this validation from your type hints, no extra code required, and it surfaces through the exact same is_error=True channel as every other failure in this course. Production hardening here isn't about adding more validation code; it's about making sure your host code actually surfaces these detailed pydantic errors usefully to a user or log, instead of just showing a generic "something went wrong."

Graceful Degradation Beyond Validation

Validation catches malformed requests. Production hardening also means planning for failures validation can't catch:

  • A dependency the tool relies on is down — a database, an external API. The tool should catch this and return a clear is_error result, not let an unhandled exception propagate in a way that crashes the server process.
  • A slow tool — per Chapter 6's health-check project, wrap calls with a timeout rather than letting one slow tool hang an entire request.
  • An unrecognized protocol version — the spec defines UnsupportedProtocolVersionError for exactly this; a server should respond with a clear, structured error naming its supported versions rather than failing ambiguously.

Production Scenario: The Client Nobody Tested Against

A platform team's integration tests only ever used the modern SDK client (the default mode="auto"). A partner integration, built against an older MCP client library, connected successfully in production — the dual-era server accepted it without complaint, exactly as this chapter's proof demonstrated — but hit a subtle behavior difference: a resource that returned slightly different content shape under the legacy code path (a difference in how one internal helper handled the older request format). Because the team's tests never exercised mode="legacy", this went unnoticed until the partner reported it. The fix was two-fold: patch the actual code difference, and — more durably — add legacy-mode test coverage alongside modern-mode coverage for every server going forward, treating dual-era support as a tested guarantee, not an assumed side effect of the SDK's default behavior.

Common Mistakes

  • Assuming "the SDK supports dual-era" means "my server's behavior is identical across both eras" — per this chapter's production scenario, it means the server accepts both, not that no era-specific bugs can exist.
  • Testing only against the SDK's own default (modern) client mode, never exercising mode="legacy", even though the server accepts and serves legacy clients in production.
  • Treating pydantic's validation error messages as something to hide from users/logs rather than a genuinely useful, free diagnostic — they're detailed and specific by default.
  • Not planning for dependency failures inside tools (a database down, a timeout) separately from input validation — these are different failure classes needing different handling.

Builder Thought Process

Problem: verify, rather than assume, what actually happens when a legacy-mode client connects to a server this course built using modern-only patterns.

Assumption going in: per Chapter 3's compatibility matrix, "modern client + legacy server" fails — so a naive guess might be that legacy clients also struggle against our servers.

Test: connected a real mode="legacy" client to the exact same MCPServer instance used throughout this course.

Observed result: succeeded, with a real initialize handshake visible in debug logs — the server is dual-era by default, matching a different row of Chapter 3's matrix ("Legacy client, Dual-era server → Works") than initially assumed.

Decision: reframe the chapter around what this actually means for testing practice (cover both eras, don't assume parity) rather than around a hypothetical failure that testing disproved.

Points To Remember

  • Every server in this course is dual-era by default — the SDK serves both modern (2026-07-28) and legacy (2025-11-25) clients without extra code, confirmed with a real legacy-mode connection.
  • Dual-era support being automatic doesn't guarantee identical behavior across both eras — test both, per this chapter's production scenario.
  • Type-hint-driven validation is free and detailed (pydantic error messages) — production hardening is about surfacing it well, not adding more of it.
  • Plan separately for input validation failures, dependency failures, slow tools, and version mismatches — each needs different handling.
