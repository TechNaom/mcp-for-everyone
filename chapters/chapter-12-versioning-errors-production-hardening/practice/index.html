Chapter 12 Practice Bank ~20 min

Practice Bank: Versioning, Errors & Production Hardening

Operational judgment for shipping something that has to survive contact with reality.

Scenario · Operations

The upgrade that broke a partner

Your team upgrades the MCP SDK, and a partner's legacy-mode integration breaks. Using this chapter's proof that dual-era support is a tested guarantee (not automatic forever), what should have been in place before shipping the upgrade?

Scenario · Support

The vague error report

A user says "it gave an error." Given that validation errors include detailed pydantic messages, what does this suggest about where in the host/client stack that detail is getting lost before reaching the user or the support team?

Scenario · Cost

The retry storm

A tool that depends on an external API starts failing, and naive retry logic in the host causes a flood of repeated calls, worsening the outage. What hardening pattern (beyond simple retries) would prevent this?

Scenario · Compliance

The audit finding

An audit finds that your team has no documented policy on which MCP spec versions are supported, for how long. Using this chapter's architect interview question on compatibility governance, what's the minimum viable policy you'd draft first?

Scenario · Debugging

The bug that only appears in legacy mode

A bug report can't be reproduced with the default SDK client. Given this chapter's central finding, what's the very first thing you'd try before concluding the report is invalid?

Scenario · Eval

The missing dependency-failure test

A team's test suite covers valid inputs and invalid inputs thoroughly, but has zero tests simulating a downstream dependency being unavailable. What's the risk of this gap, and how would you prioritize closing it against other test debt?
