Chapter 4 Interview Questions ~15 min

Interview Questions: Your First MCP Server

Grouped by level. Each includes a strong answer, a red flag, and a follow-up an interviewer might ask next.

1. (Beginner) What's the difference between a tool and a resource in MCP?

Strong answer: A tool is something the model calls to perform an action or side effect — it's invoked, like a POST. A resource is data the client reads and loads into context — it's addressed by a URI, like a GET. The distinguishing question is "does calling this change anything?" — if yes, it's a tool even if it also returns data.

Red flag: Says "they're basically the same thing" or can't explain why a read with side effects should be a tool, not a resource.

Follow-up: "Where would prompts fit into this picture?"

What this proves: The candidate understands MCP's primitive model, not just "the model can call functions."

2. (Beginner) Why does the Python SDK ask for type hints on every tool parameter?

Strong answer: The SDK generates the tool's JSON Schema from type hints and the docstring, so the client and model know what arguments are valid without you writing schema by hand. Skip a type hint and the parameter falls back to an untyped/loose schema — the server still runs, but validation gets weaker silently.

Red flag: Thinks type hints are "just for readability" and doesn't connect them to schema generation or validation.

Follow-up: "What would you add to a CI pipeline to catch a missing type hint before it ships?"

What this proves: Understands the SDK isn't magic — it's mapping a familiar Python feature onto the protocol's requirements, with real consequences for skipping it.

3. (Intermediate) Walk me through what happens on the wire when a client calls a tool.

Strong answer: The client first sends a tools/list request to discover available tools and their schemas; the server responds with the catalog. When the model decides to use one, the client sends a tools/call request with the tool name and arguments as JSON-RPC; the server runs the corresponding Python function and returns its result wrapped in a content response. Under the current (2026-07-28) spec, each of these is a self-contained, stateless request — there's no persistent session to open first.

Red flag: Describes it purely in SDK terms ("you call client.call_tool()") with no idea what's happening underneath, or asserts a session/handshake is always required.

Follow-up: "What would be different if this server were built against the 2025-11-25 spec instead?"

What this proves: Can reason about the protocol independent of the convenience SDK — important once they're debugging a client that isn't behaving.

4. (Intermediate) A tool "works" in your local test but a code reviewer rejects it. What might they be flagging?

Strong answer: Several plausible answers, and a strong candidate names more than one: missing/loose type hints that widen accepted input silently; a docstring that describes internals instead of when to call the tool (hurts model tool-selection); raw exceptions instead of clear, actionable errors; no consideration of what happens once this leaves localhost — auth, rate limits, argument sanitization.

Red flag: Can only name one issue, or treats "it ran without an exception" as sufficient proof of correctness.

Follow-up: "How would you write a test that catches the loose-type-hint problem automatically?"

What this proves: Production instinct — the gap between "runs on my machine" and "ready for review."

5. (Senior) You're adding a 40th tool to a server and the agent's tool-selection accuracy is dropping. What's going on, and what do you do?

Strong answer: Every tool in the catalog is sent to the model on every turn (via tools/list), consuming context tokens and competing for the model's attention during tool selection — more tools generally means worse selection accuracy, not just higher cost. Fixes: consolidate near-identical tools behind one parameterized tool with an action field; split the server into multiple purpose-scoped servers the host only connects when relevant; tighten docstrings so each tool's purpose is unambiguous relative to its neighbors.

Red flag: Suggests only "use a smarter model" without addressing the catalog design itself.

Follow-up: "How would you measure whether a catalog restructuring actually improved selection accuracy?"

What this proves: Understands that tool design is a context-engineering problem, not just a coding problem — the kind of judgment that separates "wrote an MCP server" from "operates one at scale."

6. (Architect) You inherit a fleet of internal MCP servers, some speaking 2025-11-25 and some speaking 2026-07-28. What's your plan?

Strong answer: First, inventory: which servers/clients speak which spec version, and which hosts need to talk to both. Because the specs describe a backward-compatibility detection mechanism (clients/servers detect the counterpart's era and fall back), the immediate risk is lower than a hard break — but plan an explicit migration: prioritize high-traffic or externally-facing servers first, put version detection/logging in front of the fleet so you can see the real mix (not guess it), and set a deprecation timeline for the older spec rather than running both indefinitely. Treat this as a versioning and observability problem, not a one-time upgrade script.

Red flag: Proposes "upgrade everything at once" with no phasing, or is unaware that the specs have a defined compatibility/fallback path at all.

Follow-up: "How would you detect, in production, that a client just silently fell back to legacy compatibility mode?"

What this proves: Architect-level thinking: manages risk and observability across a fleet, not just "gets one server working."

7. (Senior) Why does an MCP tool's error come back as a flagged result instead of raising an exception on the client?

Strong answer: A tool call is a remote, cross-process invocation carried over JSON-RPC — a Python exception can't cross that boundary directly. The protocol represents a tool failure as a normal response with an error flag and a message, so any client, in any language, has one consistent way to detect a failed call: check the result, not language-specific exception machinery. It also means "the tool ran and failed" and "the tool couldn't be reached at all" are meaningfully different failure modes, and a caller needs to handle both.

Red flag: Assumes a raised ValueError automatically becomes a client-side Python exception, or has never noticed the distinction.

Follow-up: "How would you make sure your host's agent loop actually surfaces a flagged error to the user, instead of silently treating any 'complete' response as success?"

What this proves: Understands MCP as a real cross-process protocol, not just a convenient Python API.

8. (Architect) How would you decide whether a new capability belongs on an existing MCP server or a new one?

Strong answer: Weigh at least: blast radius (does a bug or compromise in the new capability expose unrelated tools on the same server?), permission boundaries (do the two capabilities need different auth/scopes — if so, that argues strongly for separate servers), tool-catalog size and selection accuracy (bundling too much into one server degrades model tool-selection, as in Q5), and operational ownership (does one team own both capabilities, or does bundling create a shared deploy/on-call surface across teams that shouldn't be coupled). No single factor dominates; a strong answer names the trade-off explicitly rather than defaulting to "always separate" or "always bundle."

Red flag: Gives a one-line rule with no trade-off reasoning, e.g. "always make a new server for each domain" without justification.

Follow-up: "Now that you've split them into two servers, how does a single host present both tool catalogs to the model as one coherent set?"

What this proves: Architect-level judgment: server boundaries are a design decision with real security, performance, and ownership consequences, not just a folder-structure choice.
