Your First MCP Server

You'll build a real MCP server in about thirty lines of Python, connect a client to it, watch it fail on purpose, and fix it — using the current MCP specification (2026-07-28) and the official Python SDK.

Say you've wired an LLM into a support tool. It can read a ticket and write a beautifully reasoned response. But it can't actually look up the customer's account, check the order status, or save a note to the case file — because none of that is text the model was trained on. It's live data behind an API, and right now, the model has no way to reach it.

The obvious fix is to write a Python function, hand it to the model as a "tool," and let the model call it. That works — for one tool, in one codebase, talking to one model provider. The moment you have five tools, two model providers, and three different applications that all want the same tools, you're rewriting the same glue code over and over, with a slightly different shape every time.

MCP exists to make that glue code a protocol instead of a bespoke integration: write the tool once, as an MCP server, and any MCP-speaking client — Claude Desktop, Claude Code, your own agent — can discover and call it the same way. This chapter builds one from scratch.

Tools, Resources, and the Server Object

An MCP server exposes up to three kinds of things to a client:

What is... a Tool? A function the model can call to do something or produce a side effect — save a note, send a message, run a query. Think of it like a POST endpoint.
What is... a Resource? Data the client can read and load into the model's context — a file, a database row, a note. Think of it like a GET endpoint. Resources are addressed by URI (for example note://todo).
What is... a Prompt? A reusable interaction template the host can surface to a user — "summarize this," "review this PR." Prompts are covered fully in Chapter 5; this chapter focuses on tools and a resource, the two primitives you'll reach for most often.

In the Python SDK (v2, matching the 2026-07-28 specification), all three are declared on one server object using decorators. The SDK reads your function's type hints and docstring and turns them into the JSON Schema the protocol requires — you never hand-write schema.

What Happens When a Tool Is Called

It helps to see the wire traffic once before writing code, so the code isn't magic. Under the 2026-07-28 spec, every request is self-contained — there's no connection-scoped session to set up first, unlike older MCP servers you may encounter (see the callout below).

Spec note: stateful servers you'll still see Most MCP servers deployed before mid-2026 speak the prior stable spec (2025-11-25), which opens a session with an initialize handshake before any tool call. If you connect to an older server and your client hangs waiting for a response that never comes, missing the handshake is the first thing to check — Chapter 6 covers this compatibility story in full.

Build: A Notes Server

Here's a complete, runnable MCP server: two tools and one resource, backed by an in-memory dictionary. This exact code was run against the official SDK (mcp v2.0.0) while writing this chapter — the output further down is real, not illustrative.

notes_server.py 
from mcp.server import MCPServer

mcp = MCPServer("notes")

_NOTES: dict[str, str] = {}


@mcp.tool()
def save_note(title: str, body: str) -> str:
    """Save a note under a title. Overwrites any existing note with the same title."""
    _NOTES[title] = body
    return f"Saved note '{title}' ({len(body)} characters)."


@mcp.tool()
def list_notes() -> list[str]:
    """List the titles of every saved note."""
    return list(_NOTES.keys())


@mcp.resource("note://{title}")
def read_note(title: str) -> str:
    """Read the full body of a saved note by title."""
    if title not in _NOTES:
        raise ValueError(f"No note titled '{title}'")
    return _NOTES[title]


if __name__ == "__main__":
    mcp.run(transport="stdio")

Notice what you didn't write: no JSON Schema, no request-parsing boilerplate, no manual error envelope. The docstring became the tool's description; the type hints became its input/output schema. That's the SDK's whole value proposition — "you wrote two Python functions with type hints and a docstring, the SDK does the rest."

Install and run it:

terminal 
pip install "mcp[cli]"          # requires Python 3.10+
uv run mcp dev notes_server.py  # opens the MCP Inspector UI

To connect a client programmatically instead of using the Inspector — this is what a host application actually does — the SDK ships an in-memory Client for exactly this purpose:

test_notes_server.py 
import asyncio
from mcp import Client
from notes_server import mcp


async def main() -> None:
    async with Client(mcp) as client:
        tools = await client.list_tools()
        print("TOOLS:", [t.name for t in tools.tools])

        save_result = await client.call_tool(
            "save_note", {"title": "todo", "body": "buy milk"}
        )
        print("SAVE RESULT:", save_result.content[0].text)

        listed = await client.call_tool("list_notes", {})
        print("LIST RESULT:", listed.structured_content)

        resource = await client.read_resource("note://todo")
        print("RESOURCE:", resource.contents[0].text)


asyncio.run(main())

Running it produces:

output 
TOOLS: ['save_note', 'list_notes']
SAVE RESULT: Saved note 'todo' (8 characters).
LIST RESULT: {'result': ['todo']}
RESOURCE: buy milk

Take a moment to connect this back to the wire diagram above: client.list_tools() is the tools/list exchange; client.call_tool() is tools/call. The SDK is hiding JSON-RPC from you, but it's the same protocol traffic either way.

Failure Lab: Break the Schema

Now break it on purpose. Change save_note's signature to drop the type hint on body:

notes_server.py (broken) 
@mcp.tool()
def save_note(title: str, body) -> str:   # body has no type hint
    """Save a note under a title."""
    _NOTES[title] = body
    return f"Saved note '{title}'."

Re-run test_notes_server.py. The server still starts — that's the trap. The SDK falls back to an untyped schema for body, so the tool looks valid to tools/list, but any client or host that validates arguments strictly (many do, for safety) will now accept anything — a list, a dict, None — where a string was intended.

Debugging exercise Call save_note with {"title": "x", "body": 42} instead of a string. It succeeds silently and stores the integer. Now imagine body was meant to be sanitized HTML, or a SQL fragment. This is exactly how a missing type hint becomes a real production bug three weeks later, in a code path nobody is looking at. Fix: always annotate every tool parameter, and add an integration test that calls each tool with a wrong-typed argument and asserts it's rejected.

Production Scenario: A Banking Runbook Tool

A regional bank's platform team wants an internal assistant that can look up an incident runbook by ID during an outage. The naive first version is a single tool:

runbook_server.py (naive) 
@mcp.tool()
def get_runbook(runbook_id: str) -> str:
    """Fetch a runbook's full contents by ID."""
    return db.fetch_runbook(runbook_id)   # no auth, no audit trail

This ships, works in the demo, and then fails a security review: any client that can reach this server can read any runbook, including ones for systems the requesting team has no business touching — and there's no record of who asked for what. The fix isn't more code inside the tool function; it's recognizing that "who is calling this server, and what are they allowed to see" is a host/transport-level concern (Chapter 9), not something you bolt onto each tool individually. The lesson for this chapter: a tool that "works" is not the same as a tool that's ready to expose beyond your own laptop.

Trade-Offs and Common Mistakes

ChoiceWhen it fitsWhen it doesn't
One tool per action (save_note, list_notes) Most cases — the model reasons better over small, clearly-named tools. You have 200 near-identical CRUD endpoints — consider one parameterized tool with an action field instead, or you'll blow the model's tool-list context budget.
Resource for read access (note://{title}) Data the model should be able to load into context without "deciding" to call a tool. The read has side effects (increments a counter, triggers a webhook) — that's a tool, not a resource, regardless of how "read-like" it feels.
In-memory storage (this chapter's example) Learning, prototyping, single-process demos. Anything that needs to survive a restart or be shared across server instances — swap in a real datastore before this leaves your laptop.

Common mistakes at this stage:

  • Skipping type hints "to move fast" — see the Failure Lab above.
  • Writing a docstring that describes what the function does internally instead of when a model should call it — the docstring is the only signal the model has for tool selection.
  • Returning raw exceptions instead of raising a clear ValueError with a message the model can act on (compare read_note's explicit error above).
  • Treating "it started without errors" as "it's correct" — a server with a bad schema starts fine; only a client-side test catches it.

Security Considerations

This one server is low-risk — it's local, in-memory, and has no network reach. But the shape of the risk you'll meet at scale is already visible: save_note accepts arbitrary text as body. If a future version of this server rendered notes as HTML in a web UI, or fed them back into a model's context unescaped, that arbitrary text becomes an injection vector. Treat every tool argument as untrusted input the moment the server leaves your laptop — full threat modeling is Chapters 9–10.

Performance, Cost, and Scale

At this scale (one process, one user, in-memory dict), performance and cost are non-issues — that's the point of building the simplest version first. Two things to keep in mind as this grows: (1) every tool you add increases the size of the tool catalog sent to the model on tools/list, which costs context tokens on every turn — don't expose tools "just in case." (2) stdio transport (used here) means one server process per client connection; it won't survive being shared across 100 concurrent users — that's what Streamable HTTP is for (Chapter 6).

Builder Thought Process

Problem: give a model the ability to save and retrieve notes without hand-rolling a JSON-RPC integration.

Assumptions: the SDK's type-hint-to-schema conversion is reliable enough to skip manual schema writing; an in-memory dict is fine for a first pass.

Approach considered: a single notes tool with an action parameter ("save" | "list" | "read") vs. three separate tools. Chose three separate tools — clearer names help the model pick correctly, and the tool count here is small enough that catalog size isn't a concern yet (see Performance above).

Validation: ran the in-memory Client against the server and printed real output at each step, rather than trusting that "no exceptions" meant "correct."

Observed failure: removing a type hint didn't break startup — it silently widened the accepted input, which is worse than a crash because it fails later, elsewhere.

Decision: treat "every tool parameter has a type hint" as a non-negotiable lint rule going forward, not a style preference.

Points To Remember

  • An MCP server exposes tools (actions), resources (readable data by URI), and prompts (templates) — this chapter built the first two.
  • The Python SDK turns type hints and docstrings into the protocol's JSON Schema automatically; a missing type hint doesn't crash the server, it silently widens what the tool accepts.
  • Under the 2026-07-28 spec, requests are stateless — no initialize handshake. Older servers (2025-11-25 spec) still expect one; that mismatch is a common first debugging surprise (Chapter 6).
  • "It runs without errors" is not validation — call it through a client and inspect the actual output.
  • A tool that's safe on your laptop is not automatically safe once a server is reachable by others — auth, scoping, and audit trails are separate concerns from the tool function itself (Chapter 9).
Cheat sheet 
from mcp.server import MCPServer
mcp = MCPServer("name")

@mcp.tool()
def fn(arg: str) -> str: ...      # action, has a side effect

@mcp.resource("scheme://{id}")
def fn(id: str) -> str: ...       # read-only, addressed by URI

if __name__ == "__main__":
    mcp.run(transport="stdio")    # or transport="streamable-http"
