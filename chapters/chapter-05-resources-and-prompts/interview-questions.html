Chapter 5 Interview Questions ~15 min

Interview Questions: Resources & Prompts

Grouped by level. Each includes a strong answer, a red flag, and a follow-up.

1. (Beginner) What's the difference between a static and a templated resource?

Strong answer: A static resource has a fixed URI with no parameters (like config://app) — there's exactly one of it. A templated resource has a parameterized URI (like note://{title}) representing a family of addressable items. Both are read-only, no-side-effect data, unlike tools.

Red flag: Can't give an example of each, or thinks templated resources are a kind of tool.

Follow-up: "How does a client discover which templated resources a server offers?"

What this proves: Has the vocabulary to reason about resource design, not just tools.

2. (Beginner) What does calling a prompt actually do?

Strong answer: Nothing executes — the prompt function returns text (or a structured set of messages) that the host sends to the model. It's fundamentally different from a tool call, which runs code and can have side effects.

Red flag: Describes a prompt as "a kind of tool that runs a prompt template," conflating execution with text generation.

Follow-up: "Who typically triggers a prompt — the model, or a person?"

What this proves: Distinguishes prompts from tools at the conceptual level, not just by decorator name.

3. (Intermediate) A host reports "the server has no resources" but you know the server exposes a templated note resource. What's your first hypothesis?

Strong answer: Check whether the host's discovery code calls both list_resources() and list_resource_templates() — they're separate calls, and it's common for integration code to only call the first, especially if it was originally written and tested against a server with only static resources. This is a documented real failure mode (see the chapter's production scenario), not a rare edge case.

Red flag: Jumps straight to "the server must be broken" without considering the discovery-side gap.

Follow-up: "How would you write an integration test that would have caught this before it shipped?"

What this proves: Debugs from a documented, specific failure pattern rather than guessing broadly.

4. (Intermediate) When would you build something as a resource instead of a tool, even though a tool could technically do the same job?

Strong answer: When the operation is read-only with no side effect and represents data the model should be able to load directly into context — a resource communicates "this is data" more clearly than a tool does, and lets a host pre-load it without an explicit model decision to call something. The reverse mistake (making everything a tool) works but obscures intent and can bloat the tool catalog unnecessarily, hurting model tool-selection accuracy the way Chapter 4 discussed.

Red flag: Says "it doesn't matter, they're interchangeable" — technically callable doesn't mean semantically equivalent, and the choice affects host behavior and model reasoning.

Follow-up: "Could a host decide to always load a particular resource into every conversation automatically? Could it do that with a tool?"

What this proves: Understands the primitives are a design vocabulary, not just three interchangeable ways to expose a function.

5. (Senior) Design a prompt library for a support team's MCP server. What do you need to think about beyond just writing prompt functions?

Strong answer: Prompts are explicitly human-selected, so UX matters: clear, discoverable names and descriptions (the docstring is user-facing here, arguably more than for tools), sensible default/example arguments, and versioning — if you change a prompt's wording, existing users who've built workflows around its exact output may be affected. Also worth considering: should some prompts be static text with no arguments (simplest), versus parameterized ones that need argument validation same as tools.

Red flag: Treats prompt design as identical to tool design with no acknowledgment of the human-facing, explicitly-selected nature of prompts.

Follow-up: "How would you deprecate a prompt that's actively used by several teams' workflows?"

What this proves: Recognizes prompts have a different design surface (human UX) than tools (model UX).

6. (Senior) Your resource-serving code needs to decide between exposing 500 documents as 500 static resources vs. one templated resource. Walk through the trade-off.

Strong answer: 500 static resources means list_resources() returns a 500-item list on every discovery call — expensive, and unwieldy for a host to present. One templated resource (doc://{id}) means discovery is cheap (one template entry) but the client needs to already know or discover valid IDs some other way (perhaps via a separate search tool). The templated approach almost always wins at this scale; static resources make sense only for a small, fixed set of genuinely distinct things (like app config).

Red flag: Doesn't recognize that a 500-entry static resource list is a real, measurable scaling problem, not just a style preference.

Follow-up: "If IDs aren't human-guessable, how would a model or host find the right one to request?"

What this proves: Applies the static-vs-templated distinction to a real scale decision, not just a definitional one.

7. (Architect) How would you govern prompt content across an org with dozens of MCP servers, each exposing its own prompts?

Strong answer: Because a prompt's return value becomes text sent directly to a model, ungoverned prompt content is effectively ungoverned system-prompt injection at scale — a poorly or maliciously written prompt could instruct the model in ways the host and its safety layers didn't anticipate. Treat prompts the way you'd treat any user-facing copy with model-behavior implications: a review process before a new prompt ships to production, and ideally a registry so security/compliance can audit what instructions are being sent to models across the org, not just what tools exist.

Red flag: Treats prompts as low-risk because "they're just text," missing that text sent to a model is exactly the attack surface prompt injection concerns itself with (foreshadowing Chapter 10).

Follow-up: "Should a prompt from a third-party MCP server be trusted the same way as one from an internal server?"

What this proves: Connects prompt governance to the security thinking the course builds toward in Module 5, rather than treating this chapter's content as isolated from security concerns.

8. (Architect) A product wants "smart resources" that change their returned content based on who's asking. How does this interact with MCP's resource model?

Strong answer: Nothing in the resource primitive itself carries caller identity — per Chapter 3, that information (if any) lives in _meta or is established by the host/transport layer (auth headers on Streamable HTTP, for instance), not the resource URI. A resource function can absolutely branch on caller identity if the server has access to it through its own auth/session mechanism, but that's server-side application logic layered on top of MCP, not something the protocol provides. The architectural risk: if this isn't done carefully, two different callers requesting the identical URI could get different content with no signal to the client that this happened, which breaks caching assumptions (recall Chapter 3's `cacheScope`/`ttlMs` metadata) and complicates debugging ("why did this URI return something different this time").

Red flag: Assumes the URI itself can encode identity safely, or doesn't recognize the caching/debugging implications of identity-dependent resource content.

Follow-up: "How would you signal to the client that a resource's content is caller-dependent and shouldn't be cached across users?"

What this proves: Connects resource design to protocol-level concerns (caching, identity) covered elsewhere in the course, showing systems-level rather than isolated feature thinking.
