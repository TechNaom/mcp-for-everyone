Resources & Prompts

Chapter 4 built tools. This chapter finishes the primitive set: static and templated resources (and a distinction between them that will trip you up if you don't know it), and prompts — the primitive most tutorials skip.

Say you're extending Chapter 4's notes server and someone adds a tool called get_app_config that takes no arguments and just returns a fixed string — theme settings, a version number, nothing that ever changes based on input. It works. But calling it a "tool" undersells what it actually is: it's not an action, it's data the model should be able to load into context directly. That's what a resource is for — and this chapter is about using the right primitive for the right job, not just making everything a tool because tools are what Chapter 4 taught first.

Static vs. Templated Resources

Chapter 4's note://{title} resource was templated — the URI has a variable part, filled in per call. Resources can also be static — a fixed URI with no parameters, for something like app configuration:

static vs. templated 
@mcp.resource("config://app")
def get_config() -> str:
    """Static app configuration, no parameters."""
    return "theme=dark\nmax_notes=100"

@mcp.resource("note://{title}")
def get_note(title: str) -> str:
    """Templated resource: read a note by title."""
    return f"contents of {title}"

The Gotcha: Two Separate Lists

Here's something that only shows up once you actually call the client methods — confirmed by running exactly this server:

output 
STATIC RESOURCES: [('config://app', 'get_config')]
RESOURCE TEMPLATES: [('note://{title}', 'get_note')]

client.list_resources() and client.list_resource_templates() are two separate calls, returning two separate lists. A client (or host) that only checks list_resources() will never discover note://{title} — it'll look like the server has no note-reading capability at all, even though read_resource("note://todo") works perfectly fine once you know the URI. This is exactly the kind of thing that produces a confused bug report: "the server has resources but the host can't see them."

Prompts: The Skipped Primitive

What is... a Prompt? A reusable interaction template a host can surface to a user — not something the model decides to call mid-conversation (like a tool), but something a human explicitly picks, like a slash command or a menu item. "Summarize this," "Review this PR" are prompts.

Declared the same way as tools and resources — decorator, type hints, docstring:

prompts.py 
@mcp.prompt()
def summarize(text: str) -> str:
    """Summarize a piece of text in one sentence."""
    return f"Summarize the following text in one sentence:\n\n{text}"

@mcp.prompt()
def code_review(language: str, code: str) -> str:
    """Generate a code review prompt for a snippet in a given language."""
    return f"Review this {language} code for bugs and style issues:\n\n{code}"

Calling client.get_prompt("summarize", {"text": "..."}) doesn't run anything — it returns a structured message the host hands to the model, confirmed by actually calling it:

output 
description='Summarize a piece of text in one sentence.'
messages=[PromptMessage(role='user', content=TextContent(
    type='text',
    text='Summarize the following text in one sentence:\n\na long article about mcp'
))]
result_type='complete'

A prompt function's return value (here, an f-string) becomes the text of a user-role message — the server is producing the exact text the host will send to the model, not executing anything itself. That's the core distinction from tools: a prompt returns text to be sent to a model; a tool runs code and returns a result.

Choosing the Right Primitive

QuestionAnswer → Primitive
Does calling it change anything (save, delete, send)?Yes → Tool
Is it data the model should read, with no side effect?Yes → Resource (static if fixed URI, templated if parameterized)
Is it a template of text a human explicitly picks to send to the model?Yes → Prompt

Chapter 4's exercises already asked you to reason about tool-vs-resource for a note_count() function. The same discipline applies here: don't reach for "tool" by default just because that's the first primitive you learned.

Production Scenario: The Resource Nobody Could Find

An internal docs team built an MCP server exposing company policy documents as templated resources (policy://{department}/{doc-id}). Adoption was unexpectedly low. The root cause, once someone actually inspected the host's integration code: the host was calling list_resources() only — a reasonable-looking integration that simply never called list_resource_templates(), because the engineer who wrote it tested against a demo server that only had static resources. The templated policy resources were fully functional and completely invisible to users. The fix was one line — call both list methods and merge the results — but it took a support ticket and a debugging session to find, because "resources exist but don't show up" doesn't look like a server bug from the outside.

Common Mistakes

  • Assuming list_resources() returns everything — always check list_resource_templates() too when debugging "missing" resources.
  • Building a tool for something that's really read-only data with no side effect — check the "when to use what" table before defaulting to a tool.
  • Treating a prompt's return value as if it executes something — it's just text that becomes a message; nothing runs on the server beyond generating that text.
  • Forgetting that a prompt, unlike a tool, is meant to be explicitly chosen by a person, not autonomously invoked by a model mid-conversation — designing a prompt's UX around "the model will just call it" misunderstands the primitive.

Builder Thought Process

Problem: the docs team's policy server had low adoption despite working correctly in every manual test.

Assumptions: the host's resource-discovery code was complete, since it had been working for other (static-resource) servers.

Approach: reproduced the user's experience by connecting a fresh client and calling exactly what the host called, rather than testing the server in isolation with a tool like the MCP Inspector, which surfaces both resource types by default.

Validation: confirmed list_resources() alone returned an empty list against the real policy server, while list_resource_templates() returned the expected entries — reproducing the user's exact experience.

Decision: fixed the host's discovery code to call and merge both lists, and added an integration test that asserts on a templated resource specifically, so this class of bug can't silently reappear.

Points To Remember

  • Resources can be static (fixed URI) or templated (parameterized URI) — and they're discovered through two separate client calls, list_resources() and list_resource_templates().
  • A prompt is a reusable text template a human explicitly picks; calling it returns a structured message, it doesn't execute anything.
  • Choose the primitive by asking: does it change something (tool), is it read-only data (resource), or is it a template a person selects (prompt)?
  • "The client can't see my resource" is very often a discovery bug (missing the templates call), not a server bug.
Cheat sheet 
@mcp.resource("config://app")       # static
@mcp.resource("note://{title}")     # templated

@mcp.prompt()
def name(arg: str) -> str: ...      # returns text, not executed

client.list_resources()             # static only
client.list_resource_templates()    # templated only -- check BOTH
client.get_prompt(name, args)       # -> PromptMessage list, no execution
