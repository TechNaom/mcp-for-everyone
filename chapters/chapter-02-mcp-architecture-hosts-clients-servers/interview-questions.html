Chapter 2 Interview Questions ~12 min

Interview Questions: MCP Architecture

Grouped by level. Each includes a strong answer, a red flag, and a follow-up.

1. (Beginner) What's the difference between an MCP host and an MCP client?

Strong answer: The host is the user-facing application (a chat app, an IDE). The client is the protocol connection inside the host that talks to one specific server — a host with three server connections runs three clients internally. A user interacts with the host; they never directly interact with a client.

Red flag: Uses "host" and "client" interchangeably, or says the client is a separate application a user opens.

Follow-up: "If a host disconnects from a server and reconnects, is that the same client or a new one?"

What this proves: Has internalized the roles precisely enough to reason about them, not just recite definitions.

2. (Beginner) Where does the LLM fit into the host/client/server model?

Strong answer: It doesn't have its own role — it's not a host, client, or server. The model is what the host uses internally to decide which tools to call and how to interpret results. MCP is a protocol between the host application and servers; the model is an implementation detail of the host's decision-making.

Red flag: Calls the model "the client" or "the server," or can't explain why it isn't a party in the protocol.

Follow-up: "Could you test an MCP server without any LLM involved at all? How?"

What this proves: Doesn't conflate "AI system" with "MCP protocol participant" — a common early confusion.

3. (Intermediate) Can one host connect to multiple servers at once? What does that look like?

Strong answer: Yes, and it's the common case, not an edge case. The host runs one client per server connection — e.g., a filesystem server, a database server, and an internal API server, each as an independent process, each with its own client inside the host. The host is then responsible for merging the resulting tool catalogs into whatever it presents to the model.

Red flag: Assumes a 1:1 host-to-server relationship, or doesn't know who's responsible for merging multiple servers' tool catalogs.

Follow-up: "What happens if two of those servers both expose a tool called `search`?"

What this proves: Understands the architecture scales to realistic multi-server setups, which is the norm in production, not the exception.

4. (Intermediate) Two teams both want to consume the same internal data through MCP. What organizational problem does this create that a single-consumer setup doesn't have?

Strong answer: Server ownership. Once more than one host/team depends on a server, someone has to own approving changes to it — a schema change that's fine for one consumer might break the other. This isn't a protocol problem, it's the same cross-team API ownership problem any shared internal service has, and it needs an explicit owner and change process, not an informal "whoever wrote the code" default.

Red flag: Treats this as a purely technical problem (versioning, schemas) without naming the organizational/ownership dimension.

Follow-up: "How would you version the server so both teams' consumers keep working through a schema change?"

What this proves: Recognizes that architecture decisions have organizational consequences, not just technical ones — important for anyone who'll eventually own a shared server.

5. (Senior) You're reviewing a design where a team wants to embed MCP client logic directly inside their model-serving layer instead of their application layer. What's your concern?

Strong answer: The host role is supposed to own user-facing concerns — which servers to connect to, how to merge tool catalogs, how to handle a server going down — and those are product/application decisions, not model-serving decisions. Embedding client logic in the model layer couples infrastructure that should scale and fail independently (model serving vs. tool orchestration), and makes it harder to reuse the same model-serving layer for a product that needs a different set of servers. The question to ask: does this design let you swap which servers are connected without touching the model-serving code? If not, the boundary is in the wrong place.

Red flag: No concern at all, or a purely aesthetic objection ("that's not how it's usually done") without explaining the coupling risk.

Follow-up: "How would you refactor this to restore a clean host/client boundary?"

What this proves: Can apply the host/client/server boundary as a real architectural constraint, not just a diagram to memorize.

6. (Architect) Design the ownership model for an org with 6 MCP servers and 4 hosts, all internal. What do you put in place?

Strong answer: Assign an explicit owning team per server (not per host) with a documented change/deprecation process — a schema or breaking-change proposal, a notification path to all known consuming hosts, and a versioning strategy so consumers aren't forced to update in lockstep. Maintain a registry (even a simple one) mapping servers to owners and known consumers, since "who currently depends on this" tends to go undocumented until a change breaks something. Treat each server as an internal API product, because that's what it functionally is once more than one host depends on it — the MCP protocol doesn't give you this governance for free, it only gives you the wire format.

Red flag: Proposes a purely technical solution (e.g. "just version the schema") with no mention of ownership, discovery/registry, or a change-notification process.

Follow-up: "How do you discover that a server has an undocumented 5th consumer nobody told the owning team about?"

What this proves: Architect-level thinking: treats server governance as an organizational design problem, with the protocol as only one piece of it.

7. (Senior) A host you're building needs to present tools from 5 different servers to the model as one coherent list. What design decisions does that involve?

Strong answer: At minimum: namespacing or prefixing to avoid tool-name collisions across servers (see Q3's follow-up), deciding how to handle a server that's slow or down when the list is assembled (fail the whole request, or degrade gracefully by omitting that server's tools), and deciding whether to cache the merged catalog or re-fetch it per conversation. None of this is specified by MCP itself — it's host-side design work the protocol deliberately leaves open.

Red flag: Assumes merging tool catalogs is automatic or protocol-defined, with no host-side design decisions involved.

Follow-up: "How would a user know which underlying server a given tool call actually went to, if something goes wrong?"

What this proves: Understands where MCP's responsibility ends and host-application engineering begins.

8. (Architect) Would you ever design a system where the same process acts as both a host and a server? What are the risks?

Strong answer: It's possible and sometimes reasonable (e.g., a tool that itself needs to call other MCP servers as part of fulfilling a request), but it blurs a boundary that's useful for reasoning about trust and failure isolation — a process that's both consuming and exposing capabilities has a larger attack surface and a harder-to-reason-about failure mode (is a hang because the thing you called is stuck, or because a caller is stuck waiting on you?). A defensible answer allows for it but names the trade-off explicitly rather than treating host/server as always cleanly separate processes.

Red flag: Either says "never, that's not how MCP works" (too rigid — nothing in the protocol forbids it) or sees no risk at all in combining the roles.

Follow-up: "How would you scope permissions differently for the 'acting as a server' half of that process versus the 'acting as a host' half?"

What this proves: Can reason about the host/client/server model as a set of responsibilities, not a rigid deployment topology — and sees the security implications of collapsing it.
