MCP Architecture: Hosts, Clients, Servers

Three roles, three responsibilities. Get this mental model solid now and every later chapter — servers in Module 3, clients in Module 4, security boundaries in Module 5 — slots into it cleanly.

On this page 1. Where does "the AI" actually live? 2. The three roles 3. One host, many servers 4. Mapping this onto a real product 5. Architecture view 6. Production scenario: who owns the server? 7. Common mistakes 8. Builder thought process 9. Points to remember

Chapter 1 established why MCP exists. Now: when someone says "our MCP server," which piece of the system are they actually talking about? Is the model itself the server? Is the chat app the client? Getting this wrong makes every later diagram, every debugging conversation, and every security discussion harder than it needs to be — because "the server" and "the client" mean something specific and non-obvious the first time you meet them.

The Three Roles

What is... a Host? The AI-powered application the person actually uses — Claude Desktop, an IDE with an AI assistant, a custom chat app. The host is what decides which servers to connect to and orchestrates the conversation between the model and those servers.
What is... a Client? The connection inside the host that speaks MCP to one specific server. A host that talks to three servers runs three clients — one per connection. The client handles the protocol mechanics (sending requests, parsing responses); it doesn't have its own UI or identity beyond that connection.
What is... a Server? The process that exposes tools, resources, and prompts — the notes server and bookmarks server from Chapter 4 are both MCP servers. A server doesn't know or care which host is connecting to it; it just responds to requests according to the protocol.

Notice what's not one of these three roles: the model itself. The LLM is something the host uses to decide which tools to call and how to use their results — it's not a party in the MCP conversation at all. MCP is a protocol between a host application and servers; the model is an implementation detail of how the host makes decisions.

One Host, Many Servers

The relationship is rarely one-to-one. A single host commonly connects to several servers at once — a filesystem server, a database server, an internal API server — each running as its own process, each with its own client connection from the host.

This is exactly why the N×M problem from Chapter 1 mattered: each of these servers can be reused by a completely different host tomorrow, without either side needing to know about the other's internals — only the shared protocol.

Mapping This Onto a Real Product

Take the Chapter 4 notes server as a concrete example: if you ran it with uv run mcp dev notes_server.py, the MCP Inspector web UI you connected to was acting as the host — it's the application the developer interacted with. It opened one client connection to your Python process, which was the server. No LLM was involved in that exercise at all — which is a useful thing to notice: you can fully exercise the host/client/server relationship, and debug a server end to end, without a model in the loop.

Architecture View

A useful way to keep the roles straight: the host is the only role with a user-facing identity and the only one that talks to a model. Clients are invisible infrastructure — a user never "opens a client." Servers are the only role that can be shared, unmodified, across completely different hosts and products, which is the entire point established in Chapter 1.

Production Scenario: Who Owns the Server?

A retail company's platform team builds an inventory-lookup MCP server. The customer-support chat host (owned by the support team) and the internal ops dashboard host (owned by a different team) both connect to it. Six months in, the ops team wants to add a new field to the inventory response. Who approves that change? Not the support team — they don't own the server. This is the practical consequence of the architecture: once a server has multiple host consumers, changing it becomes a cross-team coordination problem, not a unilateral decision by whichever team happens to be editing the code that day. Server ownership needs to be as explicit as any other shared internal API.

Common Mistakes

  • Calling the model "the MCP server" — the model isn't a party in the protocol at all; it's what the host uses internally to decide what to call.
  • Assuming a host can only connect to one server at a time — most real hosts (Claude Desktop, IDEs with MCP support) connect to several simultaneously.
  • Treating "client" as a user-facing product name — in casual conversation people sometimes say "MCP client" to mean the whole host application, but architecturally the client is just the protocol connection inside it.
  • Forgetting that a shared server needs real ownership once more than one host depends on it — see the production scenario above.

Builder Thought Process

Problem: two teams (support chat, ops dashboard) both want to consume the same inventory data, and initially built two separate integrations before anyone noticed the duplication.

Assumptions: both teams' hosts can speak MCP; the inventory data source is stable enough to be worth standardizing (per the Chapter 1 judgment call).

Approach: consolidate into one inventory MCP server, owned by the platform team, with both hosts as clients.

Validation: confirmed both existing bespoke integrations could be replaced with equivalent tool calls against the new server before decommissioning either one.

Observed friction: the first schema-change request came from a team that didn't own the server, surfacing the ownership question immediately.

Decision: formalize server ownership and a change-request process before the second consumer's team got frustrated waiting on undocumented informal approval.

Points To Remember

  • Host: the user-facing application; the only role that talks to the model. Client: the protocol connection inside the host, one per server. Server: the process exposing tools/resources/prompts, reusable across hosts.
  • The model itself is not a party in the MCP protocol — it's an implementation detail of how the host decides what to call.
  • One host commonly runs multiple clients, each connected to a different independent server process.
  • Once a server has more than one host depending on it, it needs real ownership and a change process — the architecture creates a coordination problem the moment reuse actually happens.
