Chapter 1 Project ~30 min · Level 1, Guided

Write an Integration-Cost Memo

A short written artifact — the kind of one-page memo that actually gets a standardization decision approved at a real company.

Before Chapter 4 has you writing MCP servers, practice the judgment call that should come first: deciding whether a tool is even worth standardizing. This project has no code — it's a one-page memo, the artifact a tech lead would actually write to get budget approved.

Build it

Pick a hypothetical (or real) organization and write a memo, no more than one page, that includes:

  • A list of 4–8 internal tools and the AI surfaces/products that need each one today (or will realistically need it within a year).
  • The bespoke-integration count (sum of tool × consumer pairs) versus the shared-protocol count (tools + consumers), shown as numbers, not just the formula.
  • A ranked recommendation: which 2–3 tools should move to MCP servers first, and why those and not the others.
  • One explicit risk your recommendation does NOT address (per the lesson's "what MCP doesn't solve" section) — security, operational burden, or something else — so the reader knows what this memo is not claiming to have solved.
Verification A strong memo passes this test: could someone who hasn't read this chapter understand your recommendation and why you ranked the tools the way you did, using only your memo? If it requires the reader to already agree that "MCP is good," it's not doing its job — it should make the case with numbers and reuse counts, the way the lesson's support-platform example did.

Why this project matters

Every chapter from here on assumes you can tell the difference between "this tool is worth building as an MCP server" and "this tool is fine as a plain function." That judgment doesn't come from knowing the protocol — it comes from being able to count and communicate the actual cost being solved, which is exactly what this memo practices.
