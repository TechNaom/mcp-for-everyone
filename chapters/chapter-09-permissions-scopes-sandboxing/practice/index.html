Chapter 9 Practice Bank ~20 min

Practice Bank: Permissions, Scopes & Sandboxing

Real security-adjacent judgment calls, not just "does the check pass."

Scenario · Security

The scope that grew

A tool originally needed notes:read only. Six months later, a small feature addition made it also need notes:write occasionally. The scope requirement was quietly widened to always require both. What's the risk in this kind of gradual scope creep, and what review practice would catch it?

Scenario · Compliance

The audit question

An auditor asks: "can you prove that only authorized users could have deleted this data?" Using this chapter's scope pattern plus Chapter 7's logging discussion, what would you need to have in place to answer confidently?

Scenario · Support

The confusing denial

A user says "the assistant won't let me delete my note, it just says an error happened." Given that permission denials look like any other is_error=True result, how should a host distinguish and communicate a permission denial specifically, rather than showing a generic error?

Scenario · Operations

The sandboxing gap

A file-processing tool correctly checks scopes before running, but once it runs, it can read any file on the server's filesystem. Is this a scope problem or a sandboxing problem? What's the fix?

Scenario · Cost

The expensive scope check

A production system's scope check calls out to a remote authorization service on every single tool call, adding meaningful latency. What caching strategy would you consider, and what security trade-off does caching a permission decision introduce?

Scenario · Eval

The permission regression

A refactor accidentally removes a @require_scope decorator from one tool during a large code cleanup. No functional test catches it, because the tool still works correctly when called with the right scope. What kind of test specifically would catch this regression?
