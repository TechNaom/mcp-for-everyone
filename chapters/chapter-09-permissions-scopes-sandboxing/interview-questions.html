Chapter 9 Interview Questions ~15 min

Interview Questions: Permissions, Scopes & Sandboxing

Grouped by level. Each includes a strong answer, a red flag, and a follow-up.

1. (Beginner) Does MCP provide any built-in permission checking?

Strong answer: No. MCP standardizes the connection and calling mechanism; permission enforcement (who can call which tool) is entirely application code a server or host builds on top, using whatever pattern fits (a decorator, middleware, infrastructure-level access control).

Red flag: Assumes MCP has a built-in ACL or permission system.

Follow-up: "If MCP doesn't provide this, why do you think it's still worth standardizing the protocol?"

What this proves: Understands this chapter's central point, consistent with Chapter 1's "what MCP doesn't solve" section.

2. (Beginner) What happens when a scope check inside a tool fails?

Strong answer: A raised PermissionError (or similar) comes back as a normal is_error=True result — exactly the same mechanism as any other tool failure covered throughout this course, not a distinct "access denied" protocol response.

Red flag: Assumes there's a special protocol-level error type for permission denials.

Follow-up: "How would a host distinguish a permission denial from a validation error, if it wanted to?"

What this proves: Connects this chapter's error handling to the pattern established since Chapter 3.

3. (Intermediate) Why is a caller-supplied scope claim, with no verification, not a real security boundary?

Strong answer: If a caller can simply state what scopes it has and be believed, anyone can claim any scope — there's no actual restriction, just a formality. A real security boundary requires the scope to come from something the caller can't forge: verified authentication (a signed token, an authenticated session) that a trusted layer establishes independently of what the caller says about itself.

Red flag: Doesn't distinguish "the caller says it has scope X" from "the system verified the caller has scope X."

Follow-up: "In this chapter's demo code, is the scope trustworthy? Why or why not?"

What this proves: Understands the difference between a real access control and a purely cosmetic one — and can apply it self-critically to the chapter's own simplified example.

4. (Intermediate) A tool is supposed to be read-only, and its code only ever issues read operations. Is that sufficient to guarantee it can't cause a write?

Strong answer: No — per this chapter's production scenario, if the tool connects with credentials that have write access, a bug or injection that causes unintended behavior (e.g., a malformed or manipulated query) can still write, because the actual constraint enforced by the code is not backed by an infrastructure-level guarantee. True read-only enforcement requires read-only credentials/permissions at the infrastructure level, not just code that happens to only write read logic today.

Red flag: Believes correct application code alone is sufficient without infrastructure-level backup.

Follow-up: "What's the minimal infrastructure change that would have prevented this chapter's production scenario?"

What this proves: Recognizes defense-in-depth as necessary, not redundant, especially against injection-class failures.

5. (Senior) Design the scope taxonomy for an MCP server exposing 15 tools across notes, calendar, and email capabilities.

Strong answer: Group by resource and action (e.g., notes:read, notes:write, calendar:read, email:send) rather than per-tool scopes, which would create 15 granular scopes that are hard to reason about and grant. Group related tools under the same scope only when they genuinely have the same risk level — sending an email is a fundamentally different risk than reading one, and should never share a scope even though both are "email" operations. Avoid one broad scope covering everything ("full access") as the default grant — that defeats the purpose.

Red flag: Proposes either one scope per tool (unwieldy) or one scope for everything (defeats least privilege), without a principled grouping rationale.

Follow-up: "How would you handle a new 16th tool that doesn't cleanly fit your existing scope categories?"

What this proves: Can design a scope taxonomy that's both usable and genuinely restrictive — a real architecture skill, not just implementing a single check.

6. (Senior) How would you test that your permission system actually enforces what you think it enforces?

Strong answer: Explicit negative tests — for every scoped tool, a test that calls it with insufficient scope and asserts is_error=True, not just tests that confirm the happy path works with correct scope. This chapter's own validation followed exactly this pattern (three scenarios: no scope, wrong scope, correct scope) — a permission system with only positive tests can silently regress to "always allow" without any test catching it.

Red flag: Only proposes testing that authorized calls succeed, missing that denial-path testing is the more important half for a security control.

Follow-up: "How would you make sure a new tool added later doesn't accidentally ship without a scope check at all?"

What this proves: Tests security controls the way security controls actually need to be tested — for failure to deny, not just failure to allow.

7. (Architect) Design the permission architecture for an MCP platform serving multiple internal teams, each with servers exposing tools of varying sensitivity.

Strong answer: Centralize identity verification and scope-granting (a real auth provider, per the SDK's AuthSettings/authenticated_principal mechanism, or an org-wide identity provider) rather than letting each server invent its own ad hoc scope system — consistency matters for auditability and for callers that need to interact with multiple servers. Require every server to declare its tools' required scopes in a discoverable, reviewable way (not just buried in code), so a security review can audit the whole platform's permission surface without reading every server's source. Sandboxing/infrastructure-level enforcement (per this chapter's production scenario) should be a platform-level requirement for sensitive operations, not something individual teams opt into inconsistently.

Red flag: Lets each team build its own incompatible permission system with no platform-level consistency or auditability.

Follow-up: "How would you retrofit this onto servers that already exist with no permission checks at all, per this chapter's opening hook?"

What this proves: Designs permission architecture as a platform capability, not a per-server afterthought — genuine architect-level thinking.

8. (Architect) A tool needs elevated scope only for a rare, specific operation (e.g., a bulk delete used once a quarter). How do you avoid granting that elevated scope broadly?

Strong answer: Consider time-bound or request-scoped elevation rather than a standing grant — a caller requests temporary elevated access for a specific justified action, which is granted, used, and expires, rather than holding a permanent broad scope "just in case." This connects to Chapter 3's Multi Round-Trip Requests pattern: a tool could return an input_required result requesting explicit elevated authorization before proceeding, rather than either always allowing (unsafe) or requiring a permanent broad grant (violates least privilege). The audit trail from this kind of just-in-time elevation is also far more useful than a standing grant that's active 99.9% of the time it's not needed.

Red flag: Defaults to "just grant the elevated scope permanently, it's simpler," missing the security and auditability cost of standing broad grants.

Follow-up: "What would the user experience look like for this kind of just-in-time elevation, from the perspective of someone using a host application?"

What this proves: Connects security architecture to protocol mechanics already covered (MRTR from Chapter 3), showing integrated systems thinking rather than treating each chapter's content in isolation.
