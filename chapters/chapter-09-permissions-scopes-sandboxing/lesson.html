Permissions, Scopes & Sandboxing

Chapter 1 promised this from day one: standardizing a tool's interface does nothing for its safety. This is the chapter that finally builds least-privilege enforcement — tested, not just described.

Every tool built in this course so far — save a note, add a bookmark, delete anything — has run with zero permission checks. Anyone who can reach the server can call anything on it. That's fine for a learning exercise; it would be a serious problem for a tool that touches real customer data, sends messages, or spends money. This chapter builds the missing piece: scoping which caller can invoke which tool, tested with both a denial and an approval to confirm it actually enforces something.

Least Privilege, Concretely

What is... least privilege? A caller should be able to do exactly what it needs, and nothing more. For an MCP server, that means: a caller with a "read notes" grant should be able to call list_notes but not delete_note — even though both are just Python functions on the same server, equally reachable over the wire.

MCP itself defines no permission model — Chapter 1 was explicit about this. What follows is one concrete pattern for building one yourself, not a protocol feature.

Build: A Scope-Enforcing Decorator

A decorator that checks a required scope against the calling context's granted scopes before letting a tool run:

scoped_notes.py 
import functools
from contextvars import ContextVar

current_scopes: ContextVar[frozenset[str]] = ContextVar(
    "current_scopes", default=frozenset()
)

def require_scope(scope: str):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            if scope not in current_scopes.get():
                raise PermissionError(f"missing required scope '{scope}'")
            return fn(*args, **kwargs)
        wrapper._required_scope = scope  # lets tooling introspect this later
        return wrapper
    return decorator

mcp = MCPServer("scoped-notes")

@mcp.tool()
@require_scope("notes:read")
def list_notes() -> list[str]:
    """List note titles."""
    return list(_NOTES.keys())

@mcp.tool()
@require_scope("notes:write")
def delete_note(title: str) -> str:
    """Delete a note by title."""
    _NOTES.pop(title, None)
    return f"deleted {title}"

Running this with three different granted-scope sets:

output 
no scope -> is_error: True  "missing required scope 'notes:write'"
read-only scope, write tool -> is_error: True  "missing required scope 'notes:write'"
read-only scope, read tool -> is_error: False  {'result': []}

Notice the failure mode: a PermissionError raised inside a tool comes back exactly the way every other tool error has throughout this course — a normal is_error=True result, not a special "access denied" protocol feature. Permission enforcement is application logic riding on the same error-reporting mechanism as any other tool failure.

What a Production System Uses Instead

The current_scopes.set(...) calls in this chapter's tests set the caller's scope directly, because there's no real caller — it's a test script. In production, that scope has to come from somewhere trustworthy: real authentication. The SDK has actual support for this — an AuthSettings object on mcp.settings.auth, and helpers like authenticated_principal() that read verified identity from the request context, tied into an OAuth-style authorization flow for HTTP transports (per the spec's own guidance: "implementations using an HTTP-based transport SHOULD conform to [the] Authorization framework"). Setting up a full OAuth authorization server is out of scope for this course's exercises, but the pattern is the same shape: some trusted layer determines the caller's granted scopes, and require_scope-style checks enforce them per tool — swap the contextvar for a real verified token, and this chapter's decorator doesn't need to change.

Sandboxing: The Other Half of Containment

Scopes control who can call what. Sandboxing controls what a tool can reach once it's called — even a properly authorized tool call shouldn't have unrestricted filesystem, network, or process access if it doesn't need it. A file-reading tool that's supposed to read from one specific directory but runs with the same privileges as the whole server process can be tricked (via a path like ../../etc/passwd) into reading anything the process can access — the tool's own input validation is the only thing standing between "read this one directory" and "read anything." Real sandboxing options include running tools in restricted subprocesses, containers with limited filesystem/network access, or OS-level permission restrictions — implementation specifics beyond this chapter's scope, but the principle is the same as scoping: grant the minimum reach a tool actually needs.

Production Scenario: The Tool With Too Much Reach

A support-tooling team built a "run diagnostic query" tool against their production database, intended for read-only troubleshooting. The tool's own code only ever issued SELECT statements — but it connected using the same database credentials as the main application, which had full read/write access. A prompt-injection-adjacent incident (a user's diagnostic request contained text that, when incorporated into a query, executed an unintended write) caused real data changes, because nothing at the infrastructure level actually restricted the tool to read-only access — the restriction existed only in the tool's own code, which turned out to be exactly the layer that failed. The fix was infrastructure-level: a separate, genuinely read-only database credential for this tool, so even a successful injection couldn't write data. This is sandboxing's core lesson: don't rely solely on a tool's own code to enforce a restriction that infrastructure can enforce more reliably.

Common Mistakes

  • Assuming MCP provides permission enforcement — it doesn't; every example in this chapter is application code layered on top.
  • Trusting a caller-supplied scope without verifying it against real authentication — a scope that's just "whatever the caller claims" isn't a security boundary at all.
  • Enforcing a restriction (like read-only access) only in a tool's own code, when the underlying infrastructure (database credentials, filesystem permissions) could enforce it more reliably — see this chapter's production scenario.
  • Granting broad scopes "to be safe" against future needs — this is the inverse of least privilege, and it's exactly what makes an eventual injection or bug more damaging than it needed to be.

Builder Thought Process

Problem: demonstrate real least-privilege enforcement on MCP tools, testably, without requiring a full OAuth server setup this course can't reasonably ask learners to stand up.

Assumptions: a contextvar-based scope check is a faithful simplification of "some trusted layer determines caller scope" — the mechanism for determining scope changes in production, but the enforcement pattern (check before running) doesn't.

Validation: ran three real scenarios — no scope, wrong scope, correct scope — against actual tool calls and confirmed each produced the expected allow/deny outcome.

Observed consistency: a permission denial comes back through the exact same is_error=True channel as every other tool failure in this course — no special protocol feature needed.

Decision: be explicit in the lesson about where the simplification is (identity verification) and where it isn't (the enforcement pattern itself), rather than either oversimplifying security or requiring infrastructure this course can't provide.

Points To Remember

  • MCP defines no permission model — every scope-checking pattern in this chapter is application code, not a protocol feature.
  • A permission denial surfaces through the same is_error=True mechanism as any other tool failure — no special protocol-level "denied" response exists.
  • Scopes control who can call what; sandboxing controls what a tool can reach once called — both matter, and neither substitutes for the other.
  • Enforcing a restriction only in a tool's own code, when infrastructure (credentials, filesystem permissions) could enforce it more reliably, is a real and common production mistake.
