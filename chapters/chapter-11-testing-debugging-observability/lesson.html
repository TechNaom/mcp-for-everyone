"It's not working" has meant something different in almost every chapter of this course — a version mismatch (Chapter 3), a dropped tool from a naive merge (Chapter 8), a missing scope check (Chapter 9), a possible injection (Chapter 10). Every one of those was diagnosed by someone able to see what actually happened on a specific request. That visibility isn't free — it has to be built in, deliberately, before the incident that needs it.

Meet Context: The Tool's Window Into the Request

Every tool function so far has taken only its declared arguments. The SDK also supports an optional Context parameter, giving a tool access to the current request without changing its public schema — the model never sees this parameter, only the declared ones:

context_basics.py 
from mcp.server.mcpserver import Context

@mcp.tool()
async def ping(ctx: Context) -> str:
    """Health check that reports request metadata."""
    meta = ctx.request_context.meta or {}
    trace_id = meta.get("traceparent", "no-trace")
    return f"pong (request_id={ctx.request_id}, traceparent={trace_id})"

Calling this with a client-supplied trace ID confirms the exact _meta shape Chapter 3 documented arrives intact:

output 
meta={'traceparent': 'trace-abc123', 'io.modelcontextprotocol/protocolVersion': '2026-07-28',
      'io.modelcontextprotocol/clientInfo': {'name': 'mcp', 'version': '0.1.0'},
      'io.modelcontextprotocol/clientCapabilities': {}}

Note that meta is a plain dict — reach for .get(), not attribute access.

A Real Deprecation, Found by Testing

Context also has ctx.info(), ctx.log(), and similar methods that send log messages back to the client over the protocol. Trying this against the installed SDK surfaced something worth knowing before you build around it:

terminal 
MCPDeprecationWarning: The logging capability is deprecated as of 2026-07-28 (SEP-2577).
  await ctx.info(f"handling ping, request_id={ctx.request_id}")

The protocol-level logging capability — sending log messages back to the connected client — is deprecated in the exact spec version this course teaches. That's not a hypothetical "watch out for this eventually"; it's the current state, confirmed by actually running the code, not read secondhand. The practical implication: build server-side observability on standard, well-understood infrastructure (Python's own logging module, feeding a real log aggregator or OpenTelemetry pipeline — recall the SDK's own OpenTelemetryMiddleware, visible if you inspect mcp.middleware) rather than the protocol's client-facing logging feature.

Build: Structured Logging With Trace Correlation

A small helper that emits one structured JSON line per event, tagged with the request ID and trace ID from _meta:

structured_logging.py 
import json, logging, time

logger = logging.getLogger("mcp-observability-demo")

def log_structured(event: str, **fields) -> None:
    """Emit one structured JSON log line."""
    logger.info(json.dumps({"event": event, "ts": time.time(), **fields}))

@mcp.tool()
async def save_note(ctx: Context, title: str, body: str) -> str:
    meta = ctx.request_context.meta or {}
    trace_id = meta.get("traceparent", "no-trace")
    start = time.monotonic()

    log_structured("tool_call_start", tool="save_note",
                    request_id=ctx.request_id, trace_id=trace_id)
    _NOTES[title] = body
    elapsed_ms = (time.monotonic() - start) * 1000
    log_structured("tool_call_end", tool="save_note", request_id=ctx.request_id,
                    trace_id=trace_id, elapsed_ms=round(elapsed_ms, 2), is_error=False)
    return f"Saved '{title}'."

Real output from calling this with a client-supplied trace ID:

output 
{"event": "tool_call_start", "ts": 1786269785.21, "tool": "save_note", "request_id": "2", "trace_id": "trace-xyz"}
{"event": "tool_call_end", "ts": 1786269785.21, "tool": "save_note", "request_id": "2", "trace_id": "trace-xyz", "elapsed_ms": 0.28, "is_error": false}

This is deliberately similar to Chapter 10's ContentFirewall logging — same idea (log every call, not just failures), formalized with structured JSON and a real trace ID a host could propagate from Chapter 7's discovery step all the way through a multi-hop call.

A Debugging Workflow That Uses This

With structured, trace-correlated logs in place, "it's not working" becomes answerable: find the trace ID for the affected request (from the host's own logs, or a user-visible request ID), filter the server's structured logs to that trace ID, and read the exact sequence of tool_call_start/tool_call_end events — including elapsed_ms and is_error — for that one request. This is exactly the workflow Chapter 6's production scenario needed and didn't have: without a trace ID tying a user's request to specific server-side log lines, "which request failed and why" is a much harder question to answer.

Production Scenario: The Incident With No Trail

A user reported that an assistant "deleted the wrong note." The support team could see, from application-level logs, that a delete_note call happened around the reported time — but with no trace ID connecting the user's session to that specific server-side call, and no structured log of what arguments were actually passed, there was no way to confirm whether the wrong title was passed by the host, whether two similarly-named notes existed, or whether the deletion tool had a bug. The incident was never conclusively resolved. The team's actual fix was retroactive: add trace-ID propagation and structured argument logging (with sensitive fields redacted, not logged verbatim) so the next occurrence would be answerable in minutes instead of unresolved indefinitely.

Common Mistakes

  • Building on the protocol's client-facing logging capability (ctx.info()/ctx.log()) without knowing it's deprecated as of the current spec — verify against the installed SDK, don't assume from older tutorials.
  • Logging only failures — Chapter 10's firewall and this chapter's pattern both log every call, because you often need the successful calls around a failure to understand what happened.
  • Logging tool arguments verbatim without considering sensitivity — per Chapter 7's interview question on this exact topic, some arguments shouldn't be logged in plaintext by default.
  • Adding observability only after an incident, rather than before — per this chapter's production scenario, the cost of "not answerable" is often higher than the cost of building logging in from the start.

Builder Thought Process

Problem: formalize the ad hoc logging this course has been building chapter by chapter (is_error checks, Chapter 10's firewall) into a real observability pattern.

Assumption going in: ctx.info() would be the natural way to add server-side logging, since it's part of the documented Context API.

Test: called it against the installed SDK to confirm the exact usage pattern before writing it into a lesson.

Observed surprise: a deprecation warning naming the exact spec version this course teaches as current — not a future concern, an already-true one.

Decision: pivot the chapter's recommended pattern to standard Python logging + trace correlation via _meta, explain the deprecation explicitly rather than quietly avoiding the deprecated API without explanation, since learners following older tutorials will hit this exact warning.

Points To Remember

  • Context gives a tool access to request_id and the request's _meta (as a plain dict) without changing the tool's model-visible schema.
  • The protocol's client-facing logging capability (ctx.info()/ctx.log()) is deprecated as of the 2026-07-28 spec — build observability on standard logging infrastructure instead.
  • Structured, trace-correlated logs (every call, not just failures) turn "it's not working" from unanswerable into a filtered log query.
  • Observability built before an incident is far more valuable than observability added after one — per this chapter's production scenario.
