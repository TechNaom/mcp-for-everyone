Chapter 11 Interview Questions ~15 min

Interview Questions: Testing, Debugging & Observability

Grouped by level. Each includes a strong answer, a red flag, and a follow-up.

1. (Beginner) What does the Context parameter give a tool function access to?

Strong answer: Request-level metadata not part of the tool's declared arguments — a request ID, the incoming `_meta` dict (protocol version, client info, custom fields like a trace ID), and helper methods for the current request — without adding anything to the schema the model sees.

Red flag: Thinks Context is part of the tool's public argument schema, or confuses it with the tool's regular parameters.

Follow-up: "Would a model ever need to know a tool uses Context internally?"

What this proves: Understands Context as server-side plumbing invisible to the model.

2. (Beginner) Why is ctx.request_context.meta.get("key") correct but ctx.request_context.meta.key wrong?

Strong answer: meta is a plain Python dict, not a Pydantic model or custom object with attribute access — confirmed by actually inspecting its type while building this chapter. Dict access (`.get()` or `[]`) is required.

Red flag: Assumes meta supports attribute access without having checked.

Follow-up: "What would happen if you tried attribute access on it anyway?"

What this proves: Pays attention to concrete, tested API details rather than assuming a convenient shape.

3. (Intermediate) Why shouldn't a new MCP server built today rely on ctx.info()/ctx.log() for its primary logging strategy?

Strong answer: That capability is deprecated as of the exact spec version (2026-07-28) this course teaches — confirmed by a real deprecation warning when calling it against the installed SDK. Building a logging strategy around a deprecated protocol feature means it may be removed in a future spec revision; standard Python logging feeding a real log aggregator is both more durable and more capable (structured fields, correlation, retention policies a protocol-level log message doesn't provide).

Red flag: Doesn't know this deprecation exists, or dismisses it as unimportant because "it still works for now."

Follow-up: "How would you find out if a deprecated feature you're relying on has been removed in a newer SDK version?"

What this proves: Takes deprecation warnings seriously and builds on durable foundations rather than the path of least resistance.

4. (Intermediate) Why log every tool call, not just the ones that fail?

Strong answer: Per this chapter's production scenario, understanding a failure often requires seeing the successful calls around it — what sequence of actions led up to the problem, what the system's state was beforehand. A logging strategy that only captures failures has no context for diagnosing them.

Red flag: Argues that logging successes is wasteful, missing the diagnostic value of surrounding context.

Follow-up: "What's the cost trade-off of logging every call versus only failures, at high request volume?"

What this proves: Balances completeness against cost with a clear rationale, not a blanket rule.

5. (Senior) Design a trace-correlation strategy spanning a host, a client connection, and a server -- referencing what Chapter 3 already established about _meta.

Strong answer: Generate (or receive, if propagated from an upstream caller) a trace ID at the host level for a given user request, pass it through every subsequent tool call via `_meta` (using the `traceparent` field, aligning with the W3C Trace Context convention Chapter 3's spec research already surfaced as a reserved `_meta` key), and have every server that receives it include it in its own structured logs. This gives an end-to-end thread from "user did X" through every server-side log line involved, across host/client/server boundaries that Chapter 2 established have no inherent visibility into each other.

Red flag: Proposes a custom, non-standard correlation ID scheme when the spec already reserves a standard field for exactly this purpose.

Follow-up: "What happens to trace correlation when a host calls two different servers to fulfill one user request?"

What this proves: Builds observability on top of what the protocol already provides rather than reinventing it, connecting Chapter 3's spec research to this chapter's practical implementation.

6. (Senior) A server's structured logs include full tool arguments in plaintext. A security review flags this. How do you respond?

Strong answer: Agree it's a real risk — per Chapter 7's interview question on this same topic, tool arguments can carry sensitive user data, and logging them verbatim by default creates a data-exposure surface in the logging system itself (which often has different access controls than the primary application). Redesign logging to redact or hash sensitive fields by default, with full-detail logging available only behind an explicit, audited debug mode — not the default production behavior.

Red flag: Defends verbatim logging as necessary for debugging without acknowledging the security trade-off, or has no redaction strategy at all.

Follow-up: "How would you debug a real production issue if the argument that mattered was redacted?"

What this proves: Balances debuggability against data protection rather than defaulting to either extreme.

7. (Architect) Design the observability platform for an org running dozens of MCP servers across multiple teams.

Strong answer: Standardize the structured log schema and trace-correlation convention (the `traceparent` field, consistent event names like `tool_call_start`/`tool_call_end`) as a platform-level contract every team's server must follow, rather than letting each team invent its own format — this is what makes cross-server tracing (Q5) actually work when a request spans multiple independently-owned servers. Centralize log aggregation and provide dashboards/alerting built on the standard schema. Treat this the same way Chapter 8's discussion of platform-level tool-naming conventions treated collision prevention: solve it once, structurally, rather than per-server.

Red flag: Lets every team build incompatible logging independently, making org-wide incident investigation impossible.

Follow-up: "How would you retrofit this standard onto servers that already have inconsistent logging in production?"

What this proves: Recognizes observability as a platform capability requiring standardization, echoing the same architectural pattern Chapter 8 established for naming.

8. (Architect) How would you decide what SLOs (service level objectives) to set for an MCP server, and how does this chapter's logging enable measuring them?

Strong answer: Candidate SLOs: tool-call success rate (derivable from `is_error` in structured logs, present in every chapter's error-handling pattern), p95/p99 latency (from `elapsed_ms`, already in this chapter's log schema), and catalog-discovery availability (does `list_tools()` succeed reliably). Each of these is directly measurable from the structured logging pattern this chapter built — the architecture decision to log every call with these fields wasn't just for debugging, it's the raw material for any SLO dashboard. Setting SLOs before this logging exists means guessing; setting them after means measuring.

Red flag: Proposes SLOs with no connection to what's actually measurable from the system's existing observability, or proposes building new instrumentation from scratch rather than reusing what this chapter's pattern already captures.

Follow-up: "Which of these SLOs would you prioritize enforcing with paging/alerting versus just dashboards?"

What this proves: Connects observability architecture directly to measurable business/reliability outcomes — the final synthesis of this chapter's technical content into an architect-level operating practice.
