Chapter 7 Intermediate ~30 min

Building an MCP Client/Host

Every chapter so far built servers. This one builds the other half — a host that discovers what a server offers and decides what to do with it — using a stand-in for the model's decision-making so the course stays runnable without an API key.

On this page 1. What a host actually does 2. The host's two jobs 3. Build: a minimal host 4. Where a real LLM fits in 5. Production scenario: the host that trusted tool names blindly 6. Common mistakes 7. Builder thought process 8. Points to remember 9. Cheat sheet

You've written five MCP servers now, and used the SDK's Client to test every one of them. But Client is not a host — it's the protocol connection Chapter 2 described. A real host wraps one or more clients, decides which tools to expose to a model, decides which tool call to actually make based on a user's request, and handles what happens when a call fails. None of that is provided by the SDK's Client — it's application code you write. This chapter writes the smallest version of that application code that still does something real.

The Host's Two Jobs

Strip away everything else, and a host does exactly two things:

  1. Discover — call list_tools() (and list_resources()/list_resource_templates() from Chapter 5) to find out what a server offers.
  2. Decide and invoke — given a user's request, pick a tool (normally an LLM's job) and call it with call_tool(), then do something with the result.

A real host's job 2 is genuinely hard — it's the entire practice of prompting a model with a tool catalog and getting a reliable decision back. This course doesn't have an LLM API key to spend (per the "no signup required" philosophy from the README), so this chapter's example uses simple keyword matching to stand in for that decision — the MCP-facing mechanics (discover, call, handle result) are identical either way, and that's what this chapter teaches.

Build: A Minimal Host

A class with exactly those two responsibilities, tested against Chapter 4's notes server:

toy_host.py 
class ToyHost:
    """Stands in for the model-driven decision loop a real host runs.
    Real hosts hand the tool catalog + user message to an LLM and let it
    decide; this uses simple keyword rules instead, to keep the course
    runnable with no API key. The MCP-facing mechanics (discover tools,
    call one, read the result) are identical either way."""

    def __init__(self, client):
        self.client = client
        self.tools_by_name = {}

    async def discover(self):
        result = await self.client.list_tools()
        self.tools_by_name = {t.name: t for t in result.tools}
        return list(self.tools_by_name.keys())

    async def handle(self, command: str) -> str:
        if command not in self.tools_by_name:
            return f"I don't know how to '{command}' -- available: {list(self.tools_by_name)}"
        result = await self.client.call_tool(command, {})
        if result.is_error:
            return f"Tool '{command}' failed: {result.content[0].text}"
        return str(result.structured_content)

Running it against the notes server:

output 
Discovered: ['save_note', 'list_notes', 'delete_note', 'search_notes', 'note_count', 'rename_note']
{'result': []}
I don't know how to 'not_a_real_tool' -- available: ['save_note', 'list_notes', ...]

Notice handle() checks result.is_error before trusting the response — Chapters 3 and 4 established that tool failures come back as normal results with a flag, not exceptions, and a host is exactly the code that has to act on that flag correctly. A host that skips this check will happily report a failed tool call as if it succeeded.

Where a Real LLM Fits In

Swap ToyHost.handle's keyword lookup for a real decision loop and the shape barely changes: hand the model the tool catalog (each tool's name, description, and input schema — exactly what list_tools() returned above), let it choose a tool and produce arguments, then call call_tool(name, arguments) with what it decided. Everything downstream — checking is_error, handling a missing tool, reporting the result — is identical to what you just built and tested. The "AI" part of an MCP host is entirely contained in step 2's decision-making; steps 1, 3, and error handling are the same protocol mechanics regardless of what's making the decision.

Production Scenario: The Host That Trusted Tool Names Blindly

A team's first host implementation passed whatever tool name a model returned straight to call_tool() with no validation against the discovered catalog. It worked in testing. In production, a model occasionally hallucinated a plausible-sounding tool name that didn't exist on the server — and because the SDK surfaces that as a normal is_error=True result rather than a crash, the host's naive "if not error, report success" logic (skipping the is_error check, unlike ToyHost.handle above) reported a confusing, garbled "success" message to the user instead of a clear "I tried to use a tool that doesn't exist" error. The fix was exactly the check this chapter's ToyHost already includes: validate the tool name against the discovered catalog before calling, and check is_error after.

Common Mistakes

  • Skipping is_error checks in host code — this is the single most common host-side bug across this course's production scenarios (Chapters 4, 6, and now 7 all hit variations of it).
  • Calling a tool name that wasn't in the discovered catalog — validate before calling, don't assume the decision-making step (model or otherwise) only ever produces valid names.
  • Re-discovering tools on every single call instead of caching the catalog for the session — wasteful, though not incorrect (per Chapter 3, nothing about statelessness requires re-discovery on every request; caching a catalog client-side is a host-level choice, not a protocol violation).
  • Treating the "decide which tool" step as MCP's job — MCP gives you the catalog and the calling mechanism; the decision logic (model-based or otherwise) is entirely host application code.

Builder Thought Process

Problem: build the smallest host that demonstrates real discover-decide-invoke mechanics without needing an LLM API key.

Assumptions: the "decide" step can be faked with simple logic without changing anything about how the "discover" and "invoke" steps work — those are pure MCP mechanics.

Approach considered: a full natural-language parser vs. a simple exact-match lookup. Chose exact-match — the teaching goal is the surrounding mechanics (catalog caching, error checking), not building a mini NLU system.

Validation: ran ToyHost against the real notes server and confirmed both the success path and the unknown-command path produce sensible output.

Decision: keep the decision logic intentionally minimal and be explicit in the lesson about what a real host replaces it with, rather than pretending keyword matching is a realistic stand-in for model reasoning.

Points To Remember

  • A host has exactly two jobs: discover what a server offers, and decide-then-invoke based on what it finds.
  • The SDK's Client is not a host — it's the protocol connection; discovery caching, decision logic, and error handling are all application code you write.
  • Checking result.is_error after every tool call is host-side code's responsibility — skipping it is this course's most repeated production bug pattern for a reason.
  • Swapping keyword-matching for a real LLM changes only the "decide" step; discovery, invocation, and error handling stay identical.
Cheat sheet 
class Host:
    async def discover(self):
        result = await self.client.list_tools()
        self.catalog = {t.name: t for t in result.tools}

    async def invoke(self, name, arguments):
        if name not in self.catalog:
            return "unknown tool"          # validate before calling
        result = await self.client.call_tool(name, arguments)
        if result.is_error:                # ALWAYS check this
            return f"failed: {result.content[0].text}"
        return result.structured_content
