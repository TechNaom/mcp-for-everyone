Transports: stdio vs. Streamable HTTP

Every server so far ran over stdio, one process per client. This chapter switches on Streamable HTTP for real — and uncovers a gotcha in the SDK's defaults that isn't obvious from the spec alone.

Every server you've built runs over stdio: one Python process, launched by the client, talking over standard input/output. That's how the MCP Inspector and Claude Desktop connect to local tools — but it only works because the client can launch a subprocess on the same machine. A server shared across a team, reachable from a web app, or load-balanced across multiple instances needs a network transport instead. That's Streamable HTTP — and getting it running correctly surfaces a default setting that will genuinely surprise you if you assumed the "stateless" spec meant "no sessions, anywhere, ever."

stdio: What It Actually Is

Per the spec: "newline-delimited messages over the standard streams of a client-launched subprocess." The client starts your Python script as a child process and talks to it over stdin/stdout — this is why every mcp.run(transport="stdio") call in this course has worked without any networking setup: there's no network involved at all. One consequence worth internalizing: the client always launches the server. You never "connect" to a pre-running stdio server the way you'd connect to a web server — the process only exists because a client started it.

Streamable HTTP: Running It For Real

Streamable HTTP is the other standard transport: a real HTTP endpoint a pre-running server exposes, that any client can connect to over the network. Switching Chapter 4's pattern to it is one line:

http_server.py 
from mcp.server import MCPServer

mcp = MCPServer("http-demo")

@mcp.tool()
def ping() -> str:
    """Simple health check tool."""
    return "pong"

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="127.0.0.1", port=8765)

Connecting a client is just as simple — swap the in-memory Client(mcp) pattern from every prior chapter for a URL:

http_client.py 
import asyncio
from mcp import Client

async def main() -> None:
    async with Client("http://127.0.0.1:8765/mcp") as client:
        tools = await client.list_tools()
        print("TOOLS:", [t.name for t in tools.tools])
        result = await client.call_tool("ping", {})
        print("RESULT:", result.structured_content)

asyncio.run(main())

Running both, in order, against the real server:

output 
TOOLS: ['ping']
RESULT: {'result': 'pong'}

The Gotcha: stateless_http Defaults to False

Chapter 3 taught that the 2026-07-28 spec is stateless — no session, every request self-contained. So a raw HTTP request to the server above, without going through the SDK's client, should just work, right? Testing it directly says otherwise:

terminal — raw request, default settings 
$ curl -X POST http://127.0.0.1:8765/mcp \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'

HTTP/1.1 400 Bad Request
mcp-session-id: 933dc6f70a134aa099b4e8b1fd8dc967
{"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Bad Request: Missing session ID"}}

A 400, demanding a session ID — on a spec whose headline feature is removing sessions. The explanation is in the SDK's own settings, not the spec: mcp.run(transport="streamable-http", ...) accepts a stateless_http parameter that defaults to False. The SDK's default Streamable HTTP behavior is session-based — practical for connection reuse and backward compatibility with tooling built around the older session model — and you must opt in explicitly to get the spec's fully stateless behavior:

http_server.py — stateless 
mcp.run(
    transport="streamable-http",
    host="127.0.0.1",
    port=8766,
    stateless_http=True,   # <- opt in explicitly
)

With that one flag added, the identical raw request — no session ID anywhere — succeeds immediately:

terminal — raw request, stateless_http=True 
HTTP/1.1 200 OK
content-type: text/event-stream

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"tools":[{"name":"ping", ...}]}}

The lesson here isn't "always set stateless_http=True." It's that a spec being stateless doesn't mean every SDK default follows it automatically — the SDK is free to make a different practical trade-off by default, and only the docs (or, as here, actually testing the raw wire behavior) will tell you which one you're getting.

Choosing a Transport

QuestionAnswer
Client and server always on the same machine, client launches the server?stdio
Server needs to be reachable over a network, by multiple clients, independently running?Streamable HTTP
Server needs to run behind a load balancer, scale horizontally?Streamable HTTP with stateless_http=True — session affinity to one instance defeats the point of load balancing
Simple local dev/debugging?stdio — no ports, no network config

Production Scenario: The Load Balancer That Couldn't Help

A platform team deployed an MCP server behind a standard HTTP load balancer, expecting requests to distribute evenly across three instances. Under load, they saw wildly uneven distribution and occasional session errors when an instance restarted. The cause: the server ran with default (session-based) Streamable HTTP settings, and the load balancer had no session affinity configured — requests within one client session were landing on different instances that didn't share session state, and the client's second request in a session would hit an instance that had never seen the session ID from the first. Two possible fixes existed: configure session-affinity routing at the load balancer (matching the session model the server was already using), or set stateless_http=True and let any instance handle any request, which is what they chose — it matched the horizontal scaling goal directly instead of working around a default they didn't need.

Common Mistakes

  • Assuming "the spec is stateless" means every deployment automatically behaves that way — the SDK's default is session-based; verify, don't assume.
  • Deploying Streamable HTTP behind a load balancer without either session affinity or stateless_http=True — pick one deliberately, per the production scenario above.
  • Testing only through the SDK's own Client, which handles session bookkeeping transparently — this can hide the exact behavior a non-SDK caller (a different language's client, a raw integration) would actually see.
  • Using stdio for a server that needs to be shared across multiple independently-running clients — stdio is fundamentally one-client-launches-one-process.

Builder Thought Process

Problem: confirm whether Chapter 3's "stateless spec" claim actually holds when running Streamable HTTP with default settings.

Assumption going in: a raw request with no session bookkeeping should just work, since the spec removed the handshake.

Test: ran the server with default settings and sent a raw curl request with no session header.

Observed failure: a 400 demanding a session ID — contradicting the assumption.

Investigation: inspected mcp.run_streamable_http_async's signature directly rather than guessing, and found stateless_http: bool = False as an explicit default.

Validation: re-ran the identical raw request against a server started with stateless_http=True — succeeded immediately, confirming the SDK setting, not the spec, was the deciding factor.

Decision: document this as a "check the SDK default, don't assume the spec's philosophy" lesson, since it's exactly the kind of gap that only shows up by testing the wire behavior directly.

Points To Remember

  • stdio: one client-launched subprocess, no networking — the transport every prior chapter used.
  • Streamable HTTP: a real network endpoint, reachable by independently-running clients, required for shared/scaled deployments.
  • The SDK's Streamable HTTP defaults to session-based (stateless_http=False) even though the current spec is stateless — confirmed by testing raw requests, not assumed from the spec's philosophy.
  • Behind a load balancer, either configure session affinity or set stateless_http=True — don't deploy without deciding.
Cheat sheet 
# stdio (local, one client launches one process)
mcp.run(transport="stdio")

# Streamable HTTP, session-based (SDK default)
mcp.run(transport="streamable-http", host="0.0.0.0", port=8000)

# Streamable HTTP, truly stateless (matches the 2026-07-28 spec)
mcp.run(transport="streamable-http", host="0.0.0.0", port=8000,
         stateless_http=True)

# Client: swap Client(mcp) for a URL string, everything else identical
Client("http://host:port/mcp")
