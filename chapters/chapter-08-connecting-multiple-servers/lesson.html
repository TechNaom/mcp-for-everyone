Connecting Multiple Servers to One Agent

Chapter 2 promised this: two servers, one host, a real tool-name collision reproduced and fixed — not a hypothetical, an actual bug you can trigger.

On this page 1. Two servers, one host 2. Reproducing the collision 3. The fix: namespacing 4. Routing calls back to the right server 5. Production scenario: the silently shadowed tool 6. Common mistakes 7. Builder thought process 8. Points to remember 9. Cheat sheet

Chapter 2 showed a diagram: one host, three clients, three independent servers, "each server has no idea the other two exist." That independence is exactly the problem this chapter solves — two servers built by two different teams can easily both expose a tool called search, and neither team did anything wrong. The host is the only place that can see both catalogs at once, so resolving the collision is entirely the host's job.

Reproducing the Collision

Two independent servers, each with a search tool that does something completely different:

two servers, same tool name 
server_a = MCPServer("notes-service")
@server_a.tool()
def search(query: str) -> list[str]:
    """Search notes for a query."""
    return [f"note-match-for-{query}"]

server_b = MCPServer("docs-service")
@server_b.tool()
def search(query: str) -> list[str]:
    """Search documentation for a query."""
    return [f"doc-match-for-{query}"]

A host connecting to both and merging catalogs the obvious way — a plain dict keyed by tool name — silently loses one:

naive merge (buggy) 
merged = {}
for t in tools_a.tools:
    merged[t.name] = ("A", t)
for t in tools_b.tools:
    merged[t.name] = ("B", t)   # silently overwrites A's entry

Running this against the two real servers above:

output 
Server A tools: ['search']
Server B tools: ['search']
Naive merged catalog: {'search': 'B'}

Server A's search is completely gone from the merged catalog — not erroring, not warning, just gone. A model given this catalog can never call notes-service's search again; every "search" call it makes routes to docs-service instead, and nothing in the system tells anyone this happened.

The Fix: Namespacing

Prefix each tool name with its originating server's identifier before merging:

namespaced merge 
namespaced = {}
for t in tools_a.tools:
    namespaced[f"notes-service.{t.name}"] = ("A", t)
for t in tools_b.tools:
    namespaced[f"docs-service.{t.name}"] = ("B", t)
output 
Namespaced merged catalog: ['notes-service.search', 'docs-service.search']

Both tools survive. The trade-off: the model now sees notes-service.search instead of a plain search, which is a slightly worse name from the model's point of view but an unambiguous one — and unambiguous beats silently wrong every time.

Routing Calls Back to the Right Server

Namespacing the catalog is only half the job — when the model picks notes-service.search, the host needs to strip the prefix and route the call to the correct client:

routing 
clients_by_namespace = {"notes-service": client_a, "docs-service": client_b}

async def call_namespaced_tool(namespaced_name: str, arguments: dict):
    namespace, _, tool_name = namespaced_name.partition(".")
    client = clients_by_namespace[namespace]
    return await client.call_tool(tool_name, arguments)

This is the same discipline as Chapter 7's ToyHost, extended: discovery now merges multiple catalogs instead of one, and invocation now needs a routing step before it can call call_tool on the right client.

Production Scenario: The Silently Shadowed Tool

A platform team connected a new "documentation search" server to an existing host that already had a "notes search" server connected, using a naive dict-merge exactly like the one above. Nothing crashed. Notes search simply stopped working — support tickets came in describing the assistant "not finding" notes that definitely existed, while documentation search worked perfectly. The root cause took longer to find than it should have precisely because there was no error anywhere: the merge succeeded, the catalog looked reasonable, and only a careful diff between "tools before this deploy" and "tools after" revealed that search now pointed somewhere different. The fix was namespacing, deployed with a test that asserts the merged catalog's size equals the sum of each source catalog's size — a collision silently makes that assertion fail.

Common Mistakes

  • Merging multiple servers' tool catalogs with a plain dict-by-name, which silently drops collisions instead of erroring — always namespace, or at minimum detect and loudly reject collisions.
  • Namespacing the catalog for discovery but forgetting to route calls back correctly, leaving call_tool() calls failing with "unknown tool" because the namespace prefix was never stripped.
  • Assuming collisions are rare — with enough independently-owned servers, a name like search, get, or list reappearing is close to guaranteed, not a corner case.
  • Not testing catalog merging at all — the "size before equals size after" assertion from the production scenario is cheap and would have caught this immediately.

Builder Thought Process

Problem: confirm Chapter 2's promised collision scenario actually happens, not just plausible in theory.

Approach: built two minimal real servers, both exposing a search tool with genuinely different behavior, and merged their catalogs the way a naive host implementation would.

Validation: ran the merge and printed the result — confirmed server A's tool vanished entirely, with no error or warning anywhere in the process.

Fix: namespaced merge, then confirmed both tools survive and are individually callable through a routing layer.

Decision: recommend namespacing as the default approach for any host connecting more than one server, rather than "handle collisions if they come up" — given how easily search/get/list-style names collide, treating this as an edge case is itself the mistake.

Points To Remember

  • A naive dict-by-name merge of multiple servers' tool catalogs silently drops colliding tool names — no error, no warning.
  • Namespacing (prefixing each tool name with its server's identifier) preserves every tool, at the cost of slightly less readable names.
  • Namespacing the catalog and routing calls back to the right client are two separate steps — both are required.
  • Test catalog merging explicitly (e.g., merged size equals the sum of source sizes) — this cheaply catches collisions before they reach production.
Cheat sheet 
# Discovery: namespace every tool by server
catalog = {}
for server_name, client in clients.items():
    tools = await client.list_tools()
    for t in tools.tools:
        catalog[f"{server_name}.{t.name}"] = (client, t)

# Invocation: split the namespace, route to the right client
async def call(namespaced_name, arguments):
    server_name, _, tool_name = namespaced_name.partition(".")
    client, _ = catalog[namespaced_name]
    return await client.call_tool(tool_name, arguments)

# Test: catch collisions immediately
assert len(catalog) == sum(len((await c.list_tools()).tools) for c in clients.values())
