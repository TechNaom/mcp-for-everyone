Exercises: The MCP Message Lifecycle

Trace a real captured exchange by hand — this reuses Chapter 4's notes server, so you're inspecting a system you already understand, from a new angle.

How to run this 
pip install "mcp[cli]"
cd chapters/chapter-03-the-mcp-message-lifecycle/exercises
python starter.py   # fill in TODO 1-2 first
starter.py solution.py (reference)

1 Capture the exchange

Fill in the TODOs and run the script. You should see output like:

result_type: complete
structured_content: {'result': "Saved note 'lifecycle' (20 characters)."}
meta: {'io.modelcontextprotocol/serverInfo': {'name': 'notes', 'version': ''}}

2 Map it to the spec shape

Using the lesson's worked-trace section, write out (on paper or in a comment) what the actual JSON-RPC result response looked like on the wire for your save_note call — the jsonrpc, id, and result fields, including where resultType and _meta fit.

3 Find the missing field

The lesson's worked-trace example includes a traceparent field in the request's _meta for OpenTelemetry propagation. Your captured output doesn't show one — why not? (Hint: who is responsible for setting it, and did anything in your script ask for it?)

4 (Production-gear) Spot a legacy response

Imagine a captured response has no _meta field at all, and no resultType. Based on the lesson, what era does this response most likely come from, and what should a well-behaved modern client do with the missing resultType?

5 (Production-gear) The notification that expects no reply

Modify your script to call client.list_tools() and inspect what's returned. Is this a request/response pair or a notification? Justify your answer using the definitions from the lesson, not just what "feels right."

6 (Production-gear) Design a version check

Write pseudocode (not full implementation) for a function detect_server_era(server) that returns "modern" or "legacy", following the detection pattern described in the lesson's compatibility section.
