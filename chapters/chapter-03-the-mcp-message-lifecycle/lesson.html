The MCP Message Lifecycle

Chapter 4 showed you a wire diagram and let the SDK hide the details. This chapter opens the hood: the exact JSON-RPC shapes MCP uses, why the current spec has no handshake at all, and what actually happens when your host talks to a server built on the older spec.

In Chapter 4, client.call_tool("save_note", {...}) quietly became a request on the wire and came back as a response. That's fine for building — but the moment something goes wrong (a version mismatch, a malformed request, a server that hangs) you need to know what's actually crossing the wire, because the SDK's error messages will reference these exact shapes.

The Three JSON-RPC Message Types

Every MCP message is one of three JSON-RPC 2.0 shapes. This is the spec's own definition (2026-07-28), not a simplification:

request 
{
  "jsonrpc": "2.0",
  "id": "string or number, never null",
  "method": "tools/call",
  "params": { "...": "..." }
}
result response 
{
  "jsonrpc": "2.0",
  "id": "must match the request's id",
  "result": {
    "resultType": "complete",
    "...": "..."
  }
}
notification (one-way, no reply expected) 
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": { "...": "..." }
}

The one detail that trips people up who've used JSON-RPC before MCP: every result carries a resultType field. "complete" means the request finished normally; "input_required" means the server needs more information before it can finish — a Multi Round-Trip Request (MRTR), covered briefly below. For backward compatibility, if resultType is missing entirely (a server built on an older spec revision), clients treat that as "complete".

Where Protocol Version and Capabilities Actually Live

Chapter 4's test output showed something worth revisiting now: every response carried a field like meta={'io.modelcontextprotocol/serverInfo': {'name': 'notes', ...}}. That wasn't SDK noise — it's the protocol's _meta mechanism, and it's the answer to "if there's no handshake, how do client and server know what version and capabilities they're speaking?"

Every client request carries these fields inside params._meta:

KeyRequired?Purpose
io.modelcontextprotocol/protocolVersionYese.g. "2026-07-28" — which spec revision this request uses
io.modelcontextprotocol/clientCapabilitiesYesWhat this client supports, declared fresh on every request
io.modelcontextprotocol/clientInfoNoClient name/version, for logging and debugging only

And every server response should carry io.modelcontextprotocol/serverInfo — exactly the field you saw in Chapter 4's real test output. The spec is explicit that these *Info fields are self-reported and must not be used for security decisions — they're for display and debugging, not authentication.

A Worked Exchange, Field By Field

Here's a tools/call request against Chapter 4's notes server, constructed from the spec's defined shapes (field names and structure straight from the 2026-07-28 specification), with a request-scoped trace ID attached the way OpenTelemetry propagation works in _meta:

request: tools/call 
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "save_note",
    "arguments": { "title": "todo", "body": "buy milk" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "traceparent": "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01"
    }
  }
}
response: result 
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "content": [{ "type": "text", "text": "Saved note 'todo' (8 characters)." }],
    "_meta": {
      "io.modelcontextprotocol/serverInfo": { "name": "notes", "version": "" }
    }
  }
}

Compare this to Chapter 4's Python output — SAVE RESULT: Saved note 'todo' (8 characters). — and you can see the SDK is just unwrapping result.content[0].text for you. Nothing about that call was magic; it was this exact shape, serialized and deserialized on your behalf.

What "Stateless" Really Means

This is the headline change in the 2026-07-28 spec, and it's easy to misread as "there's no connection." There's still a connection (stdio pipe, or an HTTP endpoint) — what's gone is the idea that the connection itself carries meaning. The spec states this precisely: servers must not infer context from prior requests on the same connection, and an open stdio process is explicitly not a "conversation" or "session" — a client is free to interleave unrelated requests on the same pipe, and the server can't assume otherwise.

Practically: if you need something to persist across multiple requests (a long-running task, a multi-step workflow), the spec's answer is to pass an explicit identifier on each request that references that state server-side — not to rely on the connection remembering anything. This is exactly analogous to how a well-designed REST API doesn't use TCP connection identity to track a user's session; it uses an explicit token.

Modern vs. Legacy: The Compatibility Story

The spec calls 2026-07-28-and-later modern (stateless, per-request metadata) and 2025-11-25-and-earlier legacy (an initialize handshake opens a session). Most servers you'll encounter in the wild for a while yet were built against the legacy model. The official compatibility matrix:

ClientServerOutcome
ModernModernWorks. Version mismatches surface as a clean error; client retries with a supported version.
ModernLegacyFails — the legacy server has no concept of the modern request shape.
Dual-era (supports both)ModernWorks — stays modern.
Dual-eraLegacyWorks — falls back to initialize.
LegacyModernFails — no fall-forward mechanism for legacy clients.
LegacyDual-eraWorks — server serves legacy semantics.

The important row for you right now, building fresh servers on the current SDK: a modern client talking to a legacy server fails, and the failure is not always an obvious error — the spec notes the legacy server "may reject the request... stay silent, or even process an era-ambiguous method under legacy semantics." If a real-world server you connect to seems to hang or behave strangely with no clear error, a version-era mismatch is the first thing worth checking, before assuming your own code is wrong.

Production Scenario: The Silent Version Mismatch

A logistics company's internal coding agent (built on a modern MCP client) was pointed at a partner's warehouse-inventory MCP server, built eighteen months earlier against the legacy spec. The integration "worked" in a quick manual test — the agent successfully listed a few tools — but a specific tool call silently returned no result under certain conditions, with no error surfaced anywhere. The root cause: the legacy server was processing an era-ambiguous method under legacy semantics exactly as the compatibility table warns, and the modern client had no explicit fallback logic to detect this and retry with an initialize handshake. The fix wasn't a code change to either side — it was adding explicit era-detection on the client, per the spec's documented pattern, instead of assuming every server speaks the current spec.

Common Mistakes

  • Assuming an open stdio connection implies conversation continuity — the spec explicitly forbids servers from relying on this, and a well-behaved server won't.
  • Treating clientInfo/serverInfo as trustworthy identity for security decisions — they're self-reported and explicitly not meant for that.
  • Not handling a missing resultType — a legacy-era server won't send one; treat absence as "complete", per the spec's own backward-compatibility rule, rather than treating it as malformed.
  • Assuming a version mismatch always produces a clear, catchable error — against a legacy server it may not, per the compatibility table above.

Builder Thought Process

Problem: the logistics agent's tool calls to the partner's warehouse server intermittently returned nothing, with no visible error.

Assumptions going in: both sides spoke the current MCP spec, since both were described internally as "MCP-compatible."

Approach: captured raw request/response pairs for a failing call and compared them against the spec's documented shapes (the same exercise as this chapter's worked trace above) rather than guessing from symptoms.

Validation: the captured response was missing the modern _meta fields entirely and had a shape consistent with legacy initialize-based sessions — not a malformed modern response, a different protocol era altogether.

Observed failure mode: confirmed against the compatibility matrix — "Modern client, Legacy server" is a documented failure case, not a bug in either implementation.

Decision: added explicit era-detection on the client side (per the spec's stdio probe pattern) rather than assuming all future partner servers would be modern.

Points To Remember

  • Every MCP message is a JSON-RPC request, result response, or notification — results carry a resultType field ("complete" or "input_required").
  • Protocol version and capabilities travel in every request's _meta field, not in a one-time handshake — this is what "stateless" means.
  • An open connection (even stdio) is explicitly not a conversation — servers must not infer context between requests on the same connection.
  • A modern client talking to a legacy (pre-2026-07-28) server fails, sometimes silently — always check version-era mismatch before assuming your own code is broken.
  • clientInfo/serverInfo are self-reported, for debugging only — never a security signal.
Cheat sheet 
Request:   {jsonrpc, id, method, params}
Result:    {jsonrpc, id, result: {resultType, ...}}
Error:     {jsonrpc, id?, error: {code, message, data?}}
Notify:    {jsonrpc, method, params}   (no id, no reply)

_meta (per request, required):
  io.modelcontextprotocol/protocolVersion
  io.modelcontextprotocol/clientCapabilities

_meta (per response, recommended):
  io.modelcontextprotocol/serverInfo
