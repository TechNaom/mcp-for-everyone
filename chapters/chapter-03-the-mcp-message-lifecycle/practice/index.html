Chapter 3 Practice Bank ~20 min

Practice Bank: The MCP Message Lifecycle

Wire-level debugging judgment, grounded in the compatibility matrix and stateless-core rules from the lesson.

Scenario · Debugging

The intermittent 400

A Streamable HTTP-based MCP integration works most of the time but occasionally returns a 400 with no obvious pattern. Given what the lesson says about required _meta fields, what's a plausible cause worth checking before assuming it's a network issue?

Scenario · Cost

The chatty trace field

A team adds full OpenTelemetry traceparent/tracestate/baggage propagation to every request for observability. What's the trade-off of doing this on every single stateless request, versus a session-based protocol where this might be negotiated once?

Scenario · Support

The "it worked in testing" ticket

QA tested against a mock server that always returns modern-shaped responses. Production traffic occasionally hits a legacy partner server and behaves differently. What does this suggest about what QA's mock server should have included?

Scenario · Compliance

The audit log question

An auditor asks whether clientInfo in request _meta can be used to prove which internal team made a given tool call. Using the lesson's explicit warning about self-reported fields, how do you answer, and what would you recommend instead for genuine audit trails?

Scenario · Operations

The long-running report

A tool needs to kick off a report that takes 10 minutes to generate. Given that MCP requests are stateless and an open connection isn't a "conversation," sketch (in a sentence or two) how you'd design this without relying on the connection staying open and "remembering" the in-progress report.

Scenario · Eval

The version-pinned test suite

Your integration test suite only tests against a modern (2026-07-28) mock server. Your org has 6 servers still on the legacy spec. What's missing from your test coverage, and what's one concrete test case you'd add?
