Chapter 3 Project ~30 min · Level 1, Guided

Build a Message-Lifecycle Logger

The kind of debug logging you'd actually reach for when diagnosing the "silent version mismatch" production scenario from the lesson.

Reuses Chapter 4's notes server again — this time you're wrapping every tool call with a trace that prints what went out and what came back, the same discipline the lesson's logistics-company scenario needed to find their silent failure.

starter.py solution.py (reference)

Build it

Implement traced_call in starter.py: print the outgoing call shape, time the call, then print result_type, is_error, and meta from the response. Then do TODO 4: call a tool that doesn't exist and observe — don't assume — what actually comes back. The reference solution's first draft assumed this would raise a Python exception; running it proved that wrong (it's a normal is_error=True result, same as any other tool failure), which is exactly the kind of assumption this exercise is designed to catch.

Verification Expect output shaped like: 
>> tools/call  name='save_note'  arguments={'title': 'trace-demo', 'body': 'hello'}
<< result_type='complete'  is_error=False  meta={...}  (48.29ms)
and for the nonexistent-tool call, is_error=True with the same result_type='complete' shape — not a crash.
Extension challenge Add a fourth field to your trace: a simple heuristic that flags "possible legacy-era response" if meta is empty or missing serverInfo, per the compatibility discussion in the lesson. You won't be able to test this against a real legacy server, but write the check as if you could.

Why this project matters

This is the exact tool a senior engineer reaches for the moment "it works in my manual test" stops being good enough — and it reuses code you've now touched three chapters in a row, which is deliberate: real systems get inspected from multiple angles, not built once and never revisited.
